4. THE RAMP LEG -- `zoom auto initial duration 1` (new driver f114_ramp.py)
--------------------------------------------------------------------------------
The two laws are known in closed form, so the ramp is PREDICTED, not just
measured. Let A = the total angle (~99.03 deg in this scene) and u = t/T.
  OLD  [derived from navigator.cpp:71-73 + :108, zooming_mode == -1]:
       c = coef^4 with coef advancing linearly (move.speed = 1/(duration*1000)),
       and the aim is a slerp at fraction c, so the angular progress is
       p_old(u) = A * u^4.
  NEW  [derived from Camera.cpp:365-372 (solvePlan, v0 ~ 0 branch) + :396-402]:
       t1 = T/2, a = 4A/T^2, so
       p_new(u) = 2*A*u^2            for u <= 0.5
                = A - 2*A*(1-u)^2    for u >  0.5.
       v0 is NOT exactly 0 when a plan is in flight, but at the command instant
       the camera is idle (viewT = 0) in this leg, so v0 = 0 exactly.
       T is floored at 0.2 s (Camera.cpp:932) -- inert at duration 1.
  PREDICTED DIVERGENCE (p_new - p_old), A = 99.03 deg:
       u = 0.25 :  old   0.387  new  12.379  div  11.992 deg
       u = 0.50 :  old   6.189  new  49.516  div  43.326 deg

5. THE CONVERSION'S OWN DISCRIMINATING LEG (the field config cannot do it)
--------------------------------------------------------------------------------
The field's init_view_pos is `1e-04,1e-04,1` -- the ZENITH. The conversion
(x,y,z)_old -> (y,-x,z)_camera is a 90 deg ROLL ABOUT THE ZENITH, so on this
config a correct conversion and NO conversion at all differ by only
  angle((1e-4,1e-4,1),(1e-4,-1e-4,1)) = 2.0e-04 rad = 0.0115 deg
-- 6700x the 1.7e-06 deg floor, hence detectable, but a weak criterion for a
frame error. So one extra leg on a temp-HOME FARM (the f38_scenes.sh pattern,
field config pristine, md5 asserted in == out) with
  init_view_pos = 1,0,0        (old-frame x = SOUTH)
PREDICTION: after `zoom auto initial duration 0` the two paths agree within the
floor (<= 1.0e-03 deg). With the conversion DROPPED the new path would aim at
old's (1,0,0) read as camera-frame EAST, i.e. 90.0 deg away; with the sign
dropped ((y,x,z)) it would be 180 deg away in azimuth. The leg can therefore
fail three distinguishable ways, which is why it is run.
Startup control in the same launch: the FIRST dump, before any command, must
already show the two paths in agreement at that init direction (loadCamera's own
call through the same helper) -- if the helper were wrong, startup would break
too, and that is the cheapest witness that the two sites share one home.

7. WHAT WOULD REFUTE THE WHOLE DESIGN
--------------------------------------------------------------------------------
  (a) `Camera::lookTo` being overwritten on the next frame by something else
      (a tracking re-plan, a sky-lock recapture) -- visible as g2_after's angle
      NOT closing, or closing and then re-opening between two dumps. Guarded by
      placing the call after setFlagTracking(false); if it fires anyway, the
      ordering assumption is wrong and is reported, not patched around.
  (b) The old path moving at all: any changed `navigation->` line, any old Mars
      screen value other than [1024,1024] in g1, any old angle differing from
      the PRE run by more than the scene drift. That is a construction
      violation (S11.52(b)) and aborts the delivery.
  (c) The init direction being read from a DIFFERENT source than old's
      InitViewPos (e.g. re-reading the config at the site): the fix must use
      Core's own member, so that a future `set init_view_pos`-class command
      moves both paths together.
