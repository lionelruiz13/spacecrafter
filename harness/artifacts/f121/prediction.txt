2. THE LAWS, READ FROM THE SOURCE, AND WHAT THEY IMPLY
-------------------------------------------------------
L1  FOV, auto-zoom. OLD (Projector::updateAutoZoom, projector.cpp):
      fov = start + (aim-start)*c,  c = 1-(1-k)^3 if start>aim or manual_zoom,
                                    c = k^3       otherwise;   k += speed*dt
    i.e. LINEAR IN FOV with a one-sided cubic ease.
    NEW (Camera::setHalfFov + Camera::update, Camera.cpp:668-676, 1058-1099):
      halfFov = src * (dst/src)^q,  q = 2k^2 (k<=0.5), 1-2(1-k)^2 (k>0.5)
    i.e. GEOMETRIC (log-linear) in fov with a SYMMETRIC two-phase ease.
    Same endpoints, same duration, different family AND different easing.

L2  VIEW, auto-move. OLD (Navigator::updateVisionVector, navigator.cpp:53-142):
    slerp of the vision vector at c(move.coef) with
      zooming_mode==1  : c = 1-(1-1.11k)^3 for k<=0.9, then 1
      zooming_mode==-1 : c = k^4
      otherwise        : c = atan(4(2k-1))/atan(4)/2 + 0.5
    NEW: Camera::lookTo plans a two-phase constant-|a| great-circle move with
    T floored at 0.2 s (Camera.cpp:932), and while Camera::target is set
    update() RE-PLANS every frame with (5, isMaxDuration=true), i.e.
    T = 5*(angle/pi) floored at 0.2 (Camera.cpp:664).

L3  TRACKING. OLD is a SNAP: with flag_traking set and no auto-move,
    equ_vision = selected.getEarthEquPos() every frame, no interpolation
    (navigator.cpp:127-129). NEW is a SERVO: lookTo(..., 5, true) re-planned
    each frame, so it eases in over >= 0.2 s.

L4  OBSERVER MOVE. OLD (Observer::update): mult += coef*dt, lat/alt written
    ABSOLUTELY from mult, lon accumulated -- LINEAR, no easing. NEW
    (Camera::moveRel + update): deltaPosition integrated -- also LINEAR.
    Same family.

L5  HEADING after `camera action transition_to target body`. OLD
    (AnchorManager::transitionToBody, anchor_manager.cpp) ends with
    setHeading(-axisAngle) then changeHeading(0, 5000) -- a 5 SECOND linear
    heading ramp. NEW (CameraAnchors::transitionToBody) has NO heading tail at
    all, deliberately (S11.141, A38/D28). ALREADY-ACCEPTED DELIBERATE
    DIVERGENCE -> enters the identity test as a PREDICTED RESIDUAL with its
    ledger pointer, per the F121 boundary; it is NOT reverted here.

     PREDICT |dLonDeg|, |dLatDeg| < 1e-4 deg throughout (this line moves
     neither).
     COUNTER-PREDICTION, registered because it is the interesting failure: if
     dAltMetres is instead of order the altitude itself (1e7 m), the camera's

  P4 `camera action move_to target body body_name selected duration 3

     AnchorManager::moveToBody moves the ANCHOR BODY along a straight line

  P5 `camera action transition_to target body name selected` (the last line)

5. THE FIX, PREDICTED IN SHAPE (so that what lands can be scored)
------------------------------------------------------------------
S1 FOV: single authority is FEASIBLE and cheap -- the old projector's fov is
   final for the frame at the end of Core::updateMove, and the camera's zoom
   plan is the only writer of ModularBody::halfFov after it. PREDICT the fix
   is one per-frame follow call plus killing the camera's in-flight zoom plan,
   and that it takes dFovDeg to exactly 0 on every frame of every fov
   transition, C1 included.
S2 VIEW: single authority is feasible ONLY where the two frames coincide
   (camera anchored, reference == old's home planet). PREDICT it is NOT
   feasible after `transition_to target point`, and that this is where the
   "match the interpolation at that site" carve-out has to be taken.
S3 TRACKING: making the camera SNAP like old (duration 0 in the tracking
   lookTo) is a one-token change and is predicted to take the tracking
   transient to the floor. It costs the dome-comfort smoothing D15(c) values,
   so it is predicted to be a VETO POINT rather than a free fix.
S4 HEADING: not fixable under identical-first without either reverting
   S11.141's accepted divergence or answering D28. PREDICT it STAYS RED and
   is reported.
