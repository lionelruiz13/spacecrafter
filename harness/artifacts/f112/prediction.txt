=====================================================================================
1.  THE IDENTITY CRITERION
=====================================================================================

A running process P is a SPACECRAFTER ENGINE, for the purposes of a launch precondition,
iff at least one of three channels fires:

  C (comm)  /proc/<P>/comm == "spacecrafter"
            -- world-readable, so it covers EVERY ACCOUNT; blind to any rename, because
               comm is the executable's basename truncated to 15 bytes.

  E (exe)   readlink /proc/<P>/exe resolves (after stripping a trailing " (deleted)")
            to a path X with ANY of:
              E1  basename(X) == "spacecrafter"  or  basename(X) startswith "spacecrafter"
              E2  basename(X) matches  sc_*  or  sc-*        (the staging convention:
                  sc_f109_iso, sc_post_95087b68, sc_pre_d607cfdc, sc_m1b_budget4M)
              E3  X is under /home/claude/sc-*/                (the staging-tree convention)
              E4  X contains a component matching build* immediately followed by /src/
                  (the build-tree convention: build-claude/src/spacecrafter,
                   sc-f110/tree/build/src/spacecrafter)
              E5  X == realpath($SC_BIN) when SC_BIN is set (the binary under test, exact)
            -- a real file, so no shell command line can ever match it (the F109 §11.231(j)
               self-match hazard in its other direction); covers copies and renames.

  P (port)  the process holds a LISTEN socket on TCP 7805 (the engine's server port).
            -- an engine that answers is an engine whatever its file is called.

A hit is reported as:  pid . uid . comm . exe . port . channels-that-fired.
The criterion is the UNION.  Exit 0 = no hit; exit 2 = at least one hit; exit 4 = the
probe could not run (which is a STOP, never a silent pass).

WHY THREE AND NOT ONE -- each covers the others' blind spot, and this is MEASURED, not
assumed:
  [measured 2026-09-12 15:35] `readlink /proc/121858/exe` on the owner's java (uid foxy)
  returns EMPTY, rc 1 -- /proc/<pid>/exe is NOT readable across accounts under
  yama/ptrace_scope=1 (measured: 1), while /proc/121858/comm reads "java" fine.
  So E alone cannot cover another account, and C alone cannot cover a rename.
  P covers both -- but only while the server is up.

PREDICTION 1.1: on this host, with ptrace_scope=1 and uid claude, E resolves for every
process of uid 1003 and for NO process of another uid.  REFUTED IF any other-uid pid
yields a non-empty exe here.

PREDICTION 1.2: the criterion's NEGATIVE arm is clean -- run right now, with no engine
live, the probe reports 0 hits.  REFUTED IF any of the ~600 live processes matches E2/E3/E4
by accident (the E2 `sc_*`/`sc-*` basename rule is the one at risk).  If it fires, the rule
is narrowed to E3+E4+E1 and the narrowing is recorded here, not hidden.

3.  THE RESIDUAL -- what this criterion CANNOT see, stated before it is built
=====================================================================================

R1  An engine of ANOTHER UID whose binary is renamed out of the comm match AND which has
    not opened 7805 (a --no-scene / farm launch with no server, or a launch still inside
    its first ~10 s of init).  Reason: /proc/<pid>/exe is unreadable across accounts
    (measured above); comm is the only cross-account channel and it is name-exact.
    This is the true residual and it is NOT the one the task section guessed.

R2  Same account, but the binary is renamed outside ALL of E1-E5 (basename neither
    spacecrafter* nor sc_*/sc-*), living outside /home/claude/sc-*/ and outside any
    */build*/src/*, with no server up.  Reachable in practice only by deliberately
    breaking the naming convention this corpus has used since F26.

R3  A process that has rewritten its own comm via prctl(PR_SET_NAME) while also satisfying
    R2's path conditions.  Not reachable by the engine, which never calls prctl.

R4  A LISTENING socket on 7805 held by a NON-engine (a stale socat, another project).  This
    is a FALSE POSITIVE of channel P, not a blind spot -- and it is the right behaviour:
    the port is the resource the launch needs, so "someone holds 7805" is a stop whoever
    they are.  The hit line names the holder so the reader can tell.

R5  The window between fork and exec, and the window between exec and the server's listen:
    a hit that exists but is not yet visible on E (exe already correct -- so this window is
    only P's).

NOT residual, contrary to the section's guess: "a renamed copy ... in an unlisted directory,
with no server up" is R2 and is same-account; the cross-account half (R1) is the one the
section did not name, and it is the one that actually bites, because the 2026-08-02 F26
requirement was explicitly "ANY account".

5.  THE HEADROOM GATE: the number, and where every digit comes from
=====================================================================================

The canary's present VRAM member is a NOTE at f56_canary.sh:416 against
BANK_VRAM_NOTE_MIB=8192 (:171), "NOT a gate" by its own text.  On 2026-09-12 it passed
with a note while NO launch could start (HOST-EVENTS 2026-09-12; §11.232(d)).

THE APP'S OWN STATEMENT OF ITS NEED (§11.193's anchor rule: the app states it in its own
log at init; the gate is a proxy DERIVED from that statement).

  (i) THE RED LAUNCH, artifacts/f56/canary/20260912-112628/scene/dwell.applog, the app's
      own lines in order:
        GPU memory total 32607  available 1591  used 12   free 1578
        Dedicated allocation of 512 MiB   -> used 12   (local memory 5 -> 517: the 512
                                                        fell back to HOST memory)
        Allocate chunk of 1 MiB           -> used 13
        Dedicated allocation of 160 MiB   -> used 173
        Dedicated allocation of 1280 MiB  -> used 1453 free 130
        Warn: Low GPU memory detected - release unused memory
        Dedicated allocation of 7 MiB     -> used 1461 free 122
        ERROR: Failed to allocate chunk of 256 MiB in GPU memory   (twice)
      So the INIT FLOOR -- what the app must have device-resident merely to get past the
      allocation that killed it -- is 1461 + 256 = 1717 MiB.

 (ii) THE SAME SEQUENCE ON A GREEN LAUNCH, F116's kept applogs.  Six launches of the full
      reference/real-home shape (f116/f91, f116/realhome/L01-L03, f116/smoke/L01-L02) run
      the same 22 dedicated allocations and 4 chunks and peak at the app's own
        used = 5323 MiB, 6 of 6 launches, identical to the MiB.
      Four lighter farm launches (delivered, m1, m1_seeded, smoke90) peak at 2871 MiB,
      4 of 4.  So a launch that actually loads the scene needs ~3.6x the init floor.

(iii) THE UNIT CONVERSION, measured not assumed.  The app's "available" is systematically
      BELOW what nvidia-smi calls free: on the f91 green launch the app read
      available 28984 while nvidia-smi's free was 32607 - 3179 = 29428 -- a 444 MiB
      driver/context reservation the gate's units cannot see.

  THE BANK:  BANK_GPU_NEED_MIB = 6144 MiB (6 GiB)
             = 5323 (largest measured app-resident peak)
             + 444  (the reservation of (iii))
             + ~377 rounding up to the next GiB, as the margin for scene content this
               corpus has not yet loaded.
  The gate compares nvidia-smi FREE against it and FAILS below it, on BOTH arms.

  WHY NOT the init floor (1717): a gate there would PASS a host on which the app starts,
  opens no window and dies at the next allocation -- which is a worse failure than the one
  being fixed, because it costs a launch to discover.
  WHY NOT the note threshold's complement (32607 - 8192 = 24415): that number is a guess
  from 2026-08-30 with a refuted hypothesis behind it (H-VRAM), and it would refuse this
  very host on an ordinary desktop day.
