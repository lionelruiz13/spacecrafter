**D30 — session save: EFFECTIVE-STATE snapshot, or OPERATOR-DELTA over the data?** `[B31; §11.66(a)(d), §2.0 D9, §11.55(i)]`
The save can record either (1) the *effective* value of every state item (the Moon's colour is `[1,0,0]`, its scale is 5, it is hidden), or (2) only what the operator *changed* relative to what the data declares (the operator set the Moon's colour; it was `[1,1,0.9]` in the file).
Why it matters, and it is not a style choice: under **D9** data corrections propagate FORWARD into future deliveries and the field is frozen — a user who saves a session today and reloads it after a data delivery should get the *corrected* body with their own override still on top. A snapshot freezes the values that were current at save time and silently defeats every future correction for that user; a delta does not. The design's own discriminating test (T8) is exactly this: change an authored value between save and restore and see which value wins.
Against the delta: it needs the per-body override LEDGER that does not exist today — B16 §11.55(i)'s option (2), which §11.66(a) already resolved as the target ("the in-session override ledger … is the **same authority** the cross-session save serializes"), and which B29 §11.65(f) also waits on. And it needs an identity key (D34) because a delta references bodies it does not own; a snapshot could in principle be keyed loosely.
Options: (1) snapshot; (2) delta; (3) delta for body-scoped state, snapshot for global scalars (flags, fov, time) where there is no "authored value" to be a delta from.
`[Fable rec]` (executor's rec, for the supervising session to relay or replace): **(3)** — delta where an authored value exists to be a delta from (per-body overrides, loaded content), snapshot where none does (time, observer, flags, set-values). It is not a compromise: the two halves genuinely differ, since a flag has no data-declared value that a later delivery could correct. (2) applied uniformly would force an artificial "authored default" for every flag; (1) applied uniformly loses D9's forward propagation on exactly the state a paid delivery corrects.
Fable rec for now, changes will depends on tester/user feedback.
→ **propagated §11.113(i); B31** — option (3) hybrid: delta where an authored value exists (D9's forward propagation preserved exactly there), snapshot where none does. **Recorded with the precondition of invalidation the answer states**: tester/user feedback is a reopening TRIGGER, not a scheduled revisit.

**D31 — `body action reload` vs session restore: does reload re-apply runtime overrides?** `[B31/B16/B29; §11.66(a), §11.70(g) R8, §11.55(i), §11.65(e)]`
Two recorded answers point in opposite directions for the SAME operation, and the design cannot pick between them.
- **§11.66(a)** [vixy 2026-07-22] resolved B16's suspended question as *"option (2), and larger than option (2)"* — body-scoped runtime overrides (scale, hide/show, colour) are part of saved state, and B16's landed "file wins for bodies" is *"a **partial** of this target; it is not wrong, it is incomplete"*. Read on the reload operation, that says reload should re-apply the overrides.
- **R8** [tester, §11.70(g)] says the opposite for colour: *"It must reset to the body default or color asked in the script. The user must reload the rule to be applied to it as well."* §11.70(g) recorded this as *matching* the new path's current behaviour and therefore forcing nothing — which is true only as long as reload keeps resetting.
Measured facts on the table: new-path `body action reload` REBUILDS from file, so scale 5.0 → ×1, `hidden` 1 → 4, Venus halo `[0.9,0.1,0.05]` → `[1,1,0.9]` — both entries of the reversible pair (§11.55(i), §11.65(e)); the OLD path has **no reload at all** and therefore persists everything (§11.65(d)), so there is no old observable to reproduce and §11.52(b)'s parity rule is vacuous here.
Question: after `body action reload`, are runtime body-scoped overrides (a) re-applied automatically from the ledger, or (b) discarded, with the ledger existing only for the cross-session save and the operator re-applying the rule by hand (R8's words)? A third reading is possible: (c) reload discards, and a NEW explicit verb re-applies the ledger — so both behaviours are reachable and neither is implied.
`[Fable rec]` (executor's): **(c)**. It is the only option that contradicts neither recorded answer: `body action reload` keeps meaning "re-read the file" (R8's expectation, and today's measured behaviour, so no existing script changes), while the ledger still exists and is still applied — by the session restore automatically, and in-session by an explicit act. (a) silently changes what an existing verb does to shows that already use it; (b) leaves §11.66(a)'s "incomplete, not wrong" unresolved.
The delta is whenever reset save the current state or not, tester feedback said reload is a load operation, which operate from existing saved data with either save operation or direct modification of the system file with a text editor.
(side-note : a side project, writing a tui with mouse support - a script editor with autocomplete, direct tcp mode, static analysis to report errors early and showing documentation of the currently edited call + attribute key documentation corresppnding to the key/value the cursor is on with default value shown greyed out and candidate for autocomplete when the value field is empty)
→ **propagated §11.113(j); B31; logged in FEATURE_REQUESTS.md 2026-07-29** — reload = a LOAD operation (file wins; the state-preserving route is save-then-reload, and the file may equally be a hand edit) ⇒ **the §11.66(a)-vs-R8 conflict DISSOLVES**: B16's landed behaviour is complete for that verb, the ledger belongs to the SESSION save. Rec (c)'s third verb not adopted because unneeded [veto, cheap to add later]. Side-note recorded as design input, not a decision: it makes the command grammar and the data-key vocabulary MACHINE-consumed surfaces (D10's documentation gate gains a non-human consumer), makes the TCP channel an editor-facing API, and wants defaults declared as data rather than code constants — the same authority question D12 raises from the other end.

**D32 — how deep does "as-if we continued" cut? In-flight transients.** `[B31; §11.66, §2.0 D8]`
*"as-if we continued from the time we saved"* read literally includes everything mid-flight at the save instant: an eased camera move (`Camera.hpp:367-377`), a zoom plan (`:418-421`), the view-offset arming ramp (`:402`), a body's 5-second `ASmooth` scaling ramp (`ModularBody.hpp:1619`), the time-speed ramp (`time_mgr.hpp:117-119`), atmosphere/constellation-art fades, a script's `wait` timer, a video's playback position, and a trail's accumulated points.
The two readings differ by an order of magnitude in both cost and observable. Snapping to the settled target is simple, deterministic and testable; restoring mid-flight is what the words say, but several of these have **no exact fixed point** by construction — §11.55(d) measured the tracking loop re-planning every frame with a 5 s eased profile, so "the same in-flight state" is not a well-defined target for it.
Question: (1) transients snap to their settled target on restore (a save is a still frame); (2) transients restore mid-flight wherever they have a representable state, snapping only where they demonstrably do not; (3) case by case, listed.
`[Fable rec]` (executor's): **(1)**, with one carve-out — anything the operator can SEE as a persistent condition rather than a motion must restore: the view-offset ARMED latch, the screen fader value, and (separately, see the row in the design) accumulated trail points, which are drawn content and not a motion. Argument: an operator saves a session at a moment they want to return to, not in the middle of a camera move they would have to sit through again; and a still frame is the only reading with a testable fixed point (T4 requires save→restore→save to be byte-identical, which a mid-ramp state cannot satisfy for the re-planning tracker). If you want (2), the trail/video cases are the ones worth naming explicitly, because they are the ones an audience would notice.
Fable rec, which as a side effect help diagnosing problem user could report.
→ **propagated §11.113(k); §2.0 D8 annotated (the session as-if is bounded to SETTLED state); B31** — option (1) with the stated carve-outs (view-offset armed latch, screen fader, trail points). The added reason is a new PURPOSE [derived, veto]: a file that diagnoses a user's report must be PORTABLE, which promotes the manifest from convenience to requirement (delivery identity, version, unresolved-key report) — and it reinforces the settled-state choice on independent grounds (a still frame reproduces; a mid-ramp state has no fixed point, §11.55(d)).

**D33 — trigger policy: explicit only, or autosave-at-quit / autoload-at-start?** `[B31; §2.0 D12, §11.55(h)]`
The design proposes `session action save [filename X]` / `session action load filename X` — one command registration reaching all five live channels (§11.55(h)), no config key for the ACT itself (nobody chooses "save" at startup). The open question is the POLICY: should quitting write a session automatically, and should launching restore the last one?
This is an **acting default (D12)**: it changes what launching the application means, it writes a file nobody asked for, and it makes an unattended crash or a mistaken quit part of tomorrow's starting state. For a venue running the same show nightly it is also exactly what you want.
Options: (1) explicit only; (2) opt-in via a config key (`session:autosave = <name>`, absent = off), logged on every automatic save and restore; (3) on by default.
`[Fable rec]` (executor's): **(2)**. (3) is an acting default of the widest possible reach — every operator's next launch changes — and D12's own test ("does the default cause behaviour the author did not write?") answers yes. (1) forecloses a real R2 use case (the venue that wants last night's state back) for no reason. (2) costs one key and one log line and forecloses nothing.
Explicit only, user want control and especially the ability to recover to an established clean state, most often used between sessions each time with new public (thus no continuity exists for the public).
→ **propagated §11.113(l); B31; `b31-design.md` §10's autosave row retires** — option (1), and the reason REFRAMES the row: the artifact is a PRESET (a known-good starting state, loaded repeatedly), not a resume point ⇒ load must be idempotent and repeatable, and §11.66's *"as-if we continued"* is bounded accordingly (which is what D32(1) selects independently). No acting default introduced ⇒ D12 satisfied by construction.

**D34 — cross-session identity key for the override ledger (and for non-body selections).** `[B31; A29 §5.5, A30(iii) §11.49(b), §11.109(c)]`
Persistent bodies need no new key — a script-pushed body that must survive becomes authored data in a composed system file (Vixy's own route, §11.51(a): *"save a system on-the-fly … by targeting without the .disabled or under a different name"*), so its identity is whatever an authored body's identity is. But the OVERRIDE LEDGER references bodies it does not own, and keying it by `englishName` re-imports the A29 hazard that A30(iii) already flagged for the file↔star key (*"name-matching would re-import the A29 identity-keyed hazard into a new place, decide before the first file exists"*).
Measured context: the body-name registry is **global** (`ModularBody.cpp:18`), so two systems can declare one name and the second silently loses the body (`loadBody`'s skip, `ModularSystem.cpp:963`) — that is how the §11.109(c) twin defect reached five shipped `galactic.ini` entries.
Options: (i) plain `englishName`; (ii) **system-qualified tree path** `<systemFile>::<parentChain>/<name>` — resolves cross-system collision, needs no data change and no new key, still breaks on a rename but breaks DETECTABLY; (iii) a minted stable id (`uid =`) written into the data at first save — survives renames, but is new product surface on paid data (D9), requires writing into the user's file, and legacy files have none (two-regime identity); (iv) content hash — rejected outright, since any authored edit changes identity, which defeats the D9 forward-propagation case the ledger exists to serve.
A rider that must be answered with it: **what happens when a key does not resolve at restore** (the body was renamed or removed by a data delivery). The design's answer is report-and-keep — annotate the entry inline in the session file with the reason and the valid alternatives, log once, never apply it to a near match.
The same question at a different scale governs **non-body selections** (a saved star/nebula selection needs a catalogue identifier) — folded in here so the two cannot diverge.
`[Fable rec]` (executor's): **(ii)**, with report-and-keep on a miss. It needs no data change, no new product surface and no legacy regime, and it is a prefix-compatible stepping stone to (iii) if renames ever become frequent enough to pay for a minted id. (i) is the hazard by definition.
Legacy and most testers likely expect (i), because the englishName has always been the unique identifier, enforced internally, like Unreal's AActor's unique name.
Nested naming is cleaner, agreed, but less intuitive to most users.
→ **propagated §11.113(m); B31; precedent noted at A30(iii)** — [derived] decision **(i) plain `englishName`**, on the answer's own two grounds (the identifier users know + uniqueness ENFORCED internally: global registry, duplicate-skip), with (ii)'s only structural advantage kept by putting the system-qualified path in the MISS REPORT rather than in the key. **Veto point stated**: if the two sentences describe expectation rather than the choice, this reverses at near-zero cost (machine-written session file, nothing fielded). Riders: report-and-keep adopted (uncontradicted); a restore must REPORT a miss rather than bind to a same-named body from another system (§5.40 is that failure mode); the folded non-body catalogue key is NOT answered and stays a B31 in-row design item.

**D35 — which files may the write-back rewrite: composed files only, or legacy `ssystem.ini` too?** `[B31; §11.66(b), §2.0 D9, §5.39]`
The mandate's own words are *"dynamically rewriting the stellar system files"*, which reads as including the legacy `ssystem.ini`. That file is frozen, hand-authored, paid product data; it is read by the loader's own parser; and §5.39 measured **seven keys** on the shipped file where that parser and the format parser already disagree (six whitespace-only and inert, one structural — `[Sedna]`'s malformed `orbit_LongOfPericenter 95.58754`, which the loader turns into a garbage key and the format parser drops).
Rewriting a file this engine generated (a composed twin) and rewriting the user's legacy corpus are different risk classes: the first is machine-owned and regenerable, the second is the paid product (§2.0 D9: *"corruption there is not a bug class, it is a product-destruction class"*). The §11.66(b) preservation contract exists precisely to make the second survivable — but it has not been built yet, and the whitespace-representability residual (§11.109(h2)) is still suspended, so a legacy round-trip today cannot be byte-faithful in every case.
Options: (1) composed files and the session file only — legacy stays read-only forever; (2) legacy too, but only once the preservation writer and the §5.39 parser unification are landed and gated; (3) legacy too, unconditionally, as the mandate reads.
`[Fable rec]` (executor's): **(2)**, sequenced — build the preservation writer, unify the parser, gate it on a corpus that carries a comment, a malformed line, an unknown key and an ISO-8859 value (the design's T9), and only then let it touch legacy. (1) contradicts the mandate's wording without asking you; (3) points the newest writer in the tree at the paid corpus before it has ever round-tripped one.
Option 1, legacy exists primarily for backward compatibility. The legacy format didn't support comments and it should still remains possible to revert to an older version of spacecrafter without breaking everything as long as new feature and formats aren't actively used.
→ **propagated §11.113(n); NEW DOMAIN CONSTRAINT §2.0 D13; §5.39's suspended residual dissolved** — composed + session files only, legacy read-only forever. The revert clause is general, not a B31 detail ⇒ **D13 (downgrade must stay possible)**, D9's twin: D9 = new code reads old data, D13 = old code survives what new code left behind. Operational rule: new state goes in NEW files an older build never opens (the `.ini.disabled` twin and the session file already are), never as new keys/comments/reformatting inside a file an older parser reads. Elevation from a B31-scoped answer to a general constraint is [derived] — veto point recorded at §2.0 D13.

**D36 — is a running SHOW part of the session?** `[B31; §11.66, §2.0 D8, §2(b)]`
The inventory has 15 rows whose classification is exactly this question: the script engine's play/pause state, queue position, `wait` timer, loop state and speed multiplier (`script_mgr.hpp:172-198`); script variables; loaded images and their fades; video and audio playback and position; on-dome text; subtitles; VR360/viewport; runtime-loaded catalogs.
Read literally, "save all the state so that reloading is as-if we continued" includes them: restore mid-video, mid-sentence, mid-script. That is a materially different product from "restore the sky and the observer" — it means the session file references media assets and holds playback offsets, and a restore has to re-open files that may have moved. It also interacts with §2(b) (user scripts are immutable live-show content): resuming a script mid-flight means the engine takes a position inside someone's authored artefact.
Options: (1) OUT — a session captures the observed universe and the operator's settings; a show is re-started by the operator (the script channel already exists for that); (2) IN, fully; (3) IN for the declarative parts that are cheap and stable (loaded images, on-dome text, screen fader) and OUT for the time-bearing ones (script position, video/audio playback).
`[Fable rec]` (executor's): **(3)**. The declarative parts are ordinary state and cost nothing to carry; the time-bearing ones have the same no-fixed-point problem as D32's transients plus an external-asset dependency, and an operator restoring a session almost certainly wants to re-run the show from a cue, not from a frame offset. If you read the mandate as demanding (2), say so explicitly — it roughly doubles the row's scope and adds media-asset resolution to the restore path, and neither belongs in an implementation dispatch by inference.
Fable rec (option 3).
→ **propagated §11.113(o); B31** — declarative show state IN (loaded images + fades, on-dome text, screen fader), time-bearing state OUT (script position/queue/`wait`, video and audio offsets). Coherent with D32(1) and with §2(b) — the engine never takes a position inside someone's authored script. Subtitles/VR360/viewport/runtime catalogs classify by the same rule (implementation, not a new decision).
