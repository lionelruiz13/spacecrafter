## 11. F5 addition (2026-07-25, Opus 5 executor — full record INTENT §11.109; ledger rows §5.37/§5.38, §13.B B25)

**D29 — repair the galactic path, and light up 17 star systems on every install?** `[= §5.37/§5.38; §11.109(a)/(h1); D9]`
`core.cpp:320` calls `loadGalacticSystem(".", "galactic.ini")` and the callee opens `path + name` — literally `.galactic.ini`, with no separator; the same missing separator repeats one level down for `.stellar_systems/<file>`. So on a shipped install **`galactic.ini` is never read**: no foreign star system is created, no galactic anchor is added, and (the reason this surfaced) no galactic composed twin has ever been generated. Traced to `da858612c` (2025-09-20), which replaced `AppSettings::Instance()->getUserDir()` — a path *with* its trailing `/` — by `"."` in a batch where every other call simply dropped the prefix, `main.cpp` having gained a `current_path` to the user dir. `329fa364` (2022) had split the argument correctly.
Measured rather than read (§11.109(a)), one variable per run under a temp-HOME farm: shipped tree → **0** `Params :` blocks, 0 galactic system nodes, 0 galactic twins; a **byte-identical copy of the same file under the dotted name** → **18** blocks and **17** system nodes; adding the per-system files under the dotted directory → **17** twins. Zero of 66 recorded applogs in the harness contains a `Params :` block.
The fix is one character. What it *does* is not small: 17 dead `galactic.ini` entries become 17 live `ProtoSystem`s + 17 galactic anchors (reachable through `changeSystem`/`enterSystem`, i.e. visible in the anchor surface) + 17 ModularSystem nodes in the milkyway's INNER list + 17 machine-owned files appearing in the user's `~/.spacecrafter/modularSystem/`. On this install all 13 `stellar_systems/*.ini` are **0 bytes**, so the systems arrive EMPTY; a paid delivery that ships content would arrive fully populated. That is a user-visible change to what frozen field data means (D9), which is not an executor's to take.
**Two things that must travel with the answer, not after it:**
- **§5.38 — the galactic file's own parse corrupts seven shipped coordinates.** `ssystem_factory.cpp:481` assumes exactly `key = value`; on the installed `galactic.ini` five values lose a minus sign (`Keid z`, `HelixDwarf y`, `M57Dwarf y`, `M27Dwarf y`, `NGC2392Dwarf x`) and two lose a leading digit (`M1Pulsar y = 1988.889006` → `988.889006`, `NGC2392Dwarf y = 1858.478137` → `858.478137`), because those lines have no space after `=`. **Six of the seventeen systems would appear at wrong galactic coordinates on first light.** Repairing the path without repairing the parse is worse than leaving both.
- Nothing else in B25 waits on this: the writer was exercised end-to-end on a galactic corpus without the repair (§11.109(b)), and both defects it exposed are fixed.
Question: (1) repair path + parse together now (systems appear, empty on this install); (2) repair the parse now and the path later, when a galactic data delivery exists; (3) leave both, and treat the galactic surface as retired until a delivery revives it — in which case say so, because the code currently *looks* live.
`[Fable rec]` (executor's rec, for the supervising session to relay or replace): **(1)**, in one commit, with the parse fixed first inside it. The surface is authored data that the product already ships (`galactic.ini` is in the field, with 17 entries and real coordinates), so option (3) discards paid content by inaction; option (2) leaves the repair sitting behind a second decision at exactly the moment a delivery makes it urgent. The empty-systems outcome on this install is benign and visible only as anchors — and it is what makes the 0-byte corpora *noticeable*, which is itself worth something. What deserves your eye: the anchor list grows by 17 entries for operators who never asked for them, and `changeSystem` becomes reachable for systems with no bodies.
