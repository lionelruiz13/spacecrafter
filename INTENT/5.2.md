Same single value, strictly more space. **The boolean's polarity question (b) is therefore MOOT** — the expression is deleted, not corrected; only the *default* survives as a live question, and it is now a scalar, not a polarity.
   **The navigation law is the third consumer, and it constrains the default [vixy: 2026-07-20]**, verbatim: *"The script navigate naturally by applying a multiplier on the current altitude, for joystick navigation. This is why base altitude is set to 1km by default, even though it should be more clean to set it to 0km or better, to implement the surface mode when close. […] In free movement, the velocity scale with the distance to min_radius and in free movement only it should be clamped. That is the I2 argument for the scalar, measured rather than asserted.
   **Consequence — altitude 0 is a FIXED POINT of the natural law, and that is what the 1 km base altitude patches**: at altitude 0 `distanceToReference() == 0` ⇒ `multAlt` multiplies zero ⇒ joystick altitude control is dead at the surface.    **(4) CONFIRMED + a new requirement [vixy: 2026-07-20]**: *"The multiplier should be on the proximity factor, so either relative to the true center or relative to the closest position, which make ground_radius the best candidate. With an anti-stuck mechanism to prevent being stuck and unable to takeoff when setting the height to 0 (an issue some users genuinely had and reported)."* So `multAlt` keys on `ground_radius` — the derived answer stands, on a better reason than the one I gave: the multiplier expresses *proximity*, and proximity is measured to the closest reachable position (centre when `ground_radius == 0`), not to the measurement origin. **The anti-stuck requirement is empirical — a reported user defect, now §5.18** — and it changes the fix's shape twice: (i) **the split alone does NOT fix it.** With the defaults (`datum == ground == radius`), height 0 puts the observer exactly at `ground_radius`, so the proximity factor is 0 and the multiplicative law has nothing to multiply — the reported bug survives the whole redesign unless an explicit floor lands with it; (ii) **it is not only takeoff.** All three interactive movers read the same zero — `multAlt` (radial) *and* `moveRelLon`/`moveRelLat` (free-mode lateral, `*= distanceToReference() * 5.f`) — so at proximity 0 the observer cannot move in ANY direction, not merely up.    **The anti-stuck constant ALSO already exists, unwired** [measured 2026-07-20]: `constexpr double MIN_MOVEMENT_SPEED = 0.125; //!    **FINAL SHAPE — TWO scalars, not one; names CONFIRMED [vixy: 2026-07-20]**: *"The two as separate is probably the best thing to choose and the datum_radius can default to radius, same for ground_radius, which preserve backward compatibility and enable more flexibility in the boundaries, exactly what I was looking for structurally, in fact. The naming difficulty was the diagnostic, not the obstacle: two roles resisted one name because they are two values (limits-as-design-data — the limit was in the relation, not in the candidates).
   **What the split buys, by case** (the argument for it, re-derivable): (a) solid planet — datum=ground=radius, today's behavior exactly; (b) enterable body (the two-body-patch replacement) — datum=0, ground=0: altitude reads distance-from-centre, descent to the centre allowed; (c) **terrain clearance — datum=radius, ground=radius·1.002**: altitudes stay legacy-exact while free flight cannot be driven into a mountain. **This retroactively resolves finding (i) below**: the drafted `radius*1.002f` was not a wrong number, it was the right number *assigned to the wrong role* — as a datum it broke `limLandscape` on Earth, as a ground radius it costs nothing and was what the draft wanted all along; (d) gas giant — datum at the cloud deck (altitude reads height above cloud tops, negative below), ground at 0 or a depth limit. Case (d) is only expressible BECAUSE the two are independent — a single value cannot put the measurement origin above the floor.
   **Consumer assignment [(1)-(3) follow from the definitions; (4) is DERIVED — flagged, not confirmed]**: (1) `getAltitudeReference()` → `datum_radius`, feeding `moveto altitude`, the altitude readout, and the landscape/atmosphere `lim*` thresholds; (2) the free-mode descent clamp → `ground_radius`; (3) free-mode velocity scaling → `ground_radius` (Vixy's own words attach it to the floor: *"the velocity scale with the distance to min_radius"*, min_radius being the floor concept at that point in the conversation); (4) **proposed**: the anchored/natural `multAlt` base → `ground_radius` too, NOT the datum. Reason: `multAlt` multiplies its base, so its zero is a fixed point and its sign flip is a control reversal — keyed on the datum it degenerates in case (d) (below the cloud deck, altitude goes negative and the joystick reverses), keyed on the ground it asymptotes at the floor and can never cross it. Consequence worth having: in anchored mode this gives a *soft* floor (the joystick can't reach the ground) while `moveto altitude -X` still can — safety on the interactive path with no capability foreclosed (§2(a2)). Under (a) all four collapse to today's single value, so this is regression-free by construction and only observable once the two radii differ. **Sign-off wanted on (4) before landing.**
   **Two findings the successor must carry** [measured 2026-07-20]: (i) [**superseded by the split above — the number was right, the role was wrong; kept because it is what exposed the two-role structure**] **the drafted default `radius*1.002f` is NOT legacy-compatible as an altitude zero-point** — it puts `moveto altitude 0` at 0.002·R above the surface, i.e. **12.76 km on Earth**, which is *above* `limLandscape = 10000 m` [observed: EnvironmentModule.hpp:64] ⇒ the landscape would stop showing at altitude 0 on Earth. If the nav radius is the altitude zero-point, its default must be `radius` exactly (scene E's R_mars+100 m assertion is the same constraint). The 1.002 margin only makes sense as a *separate* minimum-approach/descent floor — plausibly what `min_distance` was named for; (ii) **there is no descent floor today** — no clamp on `distance` anywhere in Camera [measured: `Camera.cpp` sites 228/383/402/601, no min/max/clamp], so nothing currently prevents descending below any surface. That means the nav radius today affects the altitude *zero-point only*, and whether it should *also* become a floor is a live design question, not an implied consequence. The two-body script patch is thereby explained precisely: going inside was always physically possible via negative altitude; what was missing was a *sane script surface* for expressing it without knowing R.
