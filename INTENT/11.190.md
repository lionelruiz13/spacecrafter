## (a) The criterion that made a prose default into a machine-readable one

D31 asks for the default value of an empty field to be shown greyed and offered
to completion. The mechanism has existed in scedit since 2026-08-04 and armed
nothing, because all **324** argument specs state their default as an English
SENTENCE (`absent -> 0`), and C2 forbids guessing a literal out of prose. The
job was to read the literals at source. **60** now exist as data, each carrying
its own `default_value_source`.

The interesting part is not the 60 — it is the rule that decided them, because
a plausible-looking default that is WRONG is worse than none. Stated in
`harness/f71_defaults.py` so it can be argued with, a literal is written only
when **both** hold:

1. **EQUIVALENCE.** Typing `<key> <literal>` produces exactly the same engine
   behaviour as omitting the key. This is what the ghost promises: it is
   offered as a completion, so accepting it puts those bytes in the buffer.
2. **NON-MISLEADING AT THE ZERO-KNOWLEDGE BAR** (C6). The literal must not
   imply membership in a vocabulary that does not exist.

The shell slice had flagged **35** prose candidates that "reduce to bare tokens
by inspection". They reproduce exactly and independently (29 zeros, 4 ones,
`no`, `180`), and **34 of the 35 survive contact with the code**. The one that
does not is the reason the second clause exists.

`camera value`'s recorded default is `absent -> no`. The word `no` satisfies
clause 1 perfectly — the handler is `bool value = valueStr == W_TRUE`
`[observed: app_command_interface.cpp:4572 @ 71ef30ac]`, so `no` and absence
both yield false. But `no` is the doc author's word for the else-branch, not a
token the engine knows. Offering it would teach that `no` means no here — and
therefore that `yes` means yes, which it does not. **A regex over the prose
would have written it.** That is the whole content of "never regexed from
prose" (C2), demonstrated rather than asserted.

The same clause excludes the FALSE side of every boolean, and the asymmetry is
a fact about the engine rather than a preference: `Utility::isTrue` accepts
exactly `TRUE`/`ON`/`1` case-folded and calls everything else false
`[observed: utility.hpp:160-171]`, so a TRUE default has a real spelling to
offer (`landscape mipmap` got `on`) and a FALSE default has none.

One exclusion is a plain measurement, not a judgment. `font size`'s default is
12, and `default_value: "12"` would be WRONG: `fontFactory.cpp:144-146` computes
`size = strToDouble(v) * fontFactor` and only THEN applies `if (size == 0)
size = 12`, so the 12 bypasses the screen scaling while a typed 12 does not.
Typing it yields `12 * fontFactor`. It fails clause 1 outright.

Also excluded, each for a stated engine reason: `landscape fov` (falls back to
`texturefov`, then 180 — no single literal reproduces absence) and the
per-branch defaults, where one literal in the spec would be wrong on the other
branches (`camera duration`, `zoom duration` — 5 on the `center` form
`[observed: app_command_interface.cpp:3422]` — `timerate step`, `dso3d
color_depth`, `media speed`, `look_at duration`, `camera filename`).

**One discriminating check inside the pass is worth recording because it could
have failed and did not.** Thirteen of the 60 are `dso3d` keys whose default
comes from a local declared `Vec3f position;` with no initialiser
`[observed: dsoNavigator.cpp:269, 296]`. Whether that is zero or INDETERMINATE
decides between "the default is 0" and a §5-class row about undefined behaviour
on the command surface. `Vector3`'s member is declared `T v[3]{}`
`[observed: vecmath.hpp:182]` — a default member initialiser with empty braces,
so value-initialised. Zero. Checked before writing, not assumed from the prose
that also says zero.

## (b) The `completable` marker: the ledger recorded one false positive, and there are five

scedit offered any `values` entry that was a bare `[A-Za-z0-9_]+` word — 166 of
the 234 distinct entries — and the mirror ledger's item 12 named ONE survivor of
that rule, `xRRGGBB`, a shape rather than a value. Listing the offerable subset
explicitly found **four more**, all from the half of the heuristic that reads
`value_docs` KEYS as values:

- `bat`, `swf`, `png` in `external_viewer.filename`. That map is keyed by file
  EXTENSION (`"avi / mov / mpg / mp4"`, `".sh"`, `"bat"`) while the values are
  `<name>.bat`; the handler also refuses anything under five characters
  `[observed: app_command_interface.cpp:2401-2448]`.
- `in` in `zoom.auto` — and this one is the `camera value` case again. It is
  typeable and it WORKS, because the domain is open: `out` and `initial` are
  recognised and every other word zooms in. The contract's own `value_docs`
  says so ("including the word 'in' itself"). Offering it would teach a
  recognised token that is not one, and would suggest `in`/`out` are a pair.

**The duplication both fields introduce is closed by a gate that checks the
strong property.** The bare-token entries of a spec's domain must be EXACTLY
accounted for — each either offered or excluded WITH A STATED REASON. A value
added later therefore cannot inherit a guess: the seed gate stays red until
somebody classifies it, and it cannot be satisfied by silence. Falsification-
tested at the touch that adds it: an unclassified token, an offered token the
domain does not hold, and a `default_value` with no source each turn their own
check red and nothing else.

## (f) One dispatcher premise did not hold, and it is reported rather than absorbed

The task section describes scope item 4 as *"first systematic read of the
rewrite's +267 unexamined lines (§11.149(e))"*. `SCRIPT_SURFACE.md` §4 is
titled *"The 267 added lines — first full pass, 2026-08-30"* and holds five
findings (SS-20…SS-25) from that pass. The lines were not unexamined.

Reported, not aborted, and the reasoning is §11.179(a)'s: the premise is an
output-side characterisation of the work rather than an input the work stands
on. What the earlier pass did was run the CHECKER — does each line PARSE as
meant. What had genuinely not been done is asking whether the new PROSE is
TRUE, which no lint rule can ask, and that is what this pass did. **Had the
premise been load-bearing — had the task depended on those lines being
unread — this would have been an abort.** Two of the earlier pass's findings
(SS-21's `(Warning!` lines, SS-24's unclosed `struct if`) were re-discovered
independently by this pass and are NOT re-minted.

Two corrections to the premise's own numbers, both measured: the delta is
**266 added / 67 removed**, not +267 (`git diff --numstat b0696413 30ea1f8d`);
and the mined revision is `b0696413`, md5 `f7f6985c…`, 1407 lines.
