## (a) The sentence has two halves that pull against each other, and both are measured

Send the feedback back; do not touch the wire it would naturally go on. The
second half is the hard one, because masterput is closed-source: what it
tolerates is TYPE-2-adjacent information, so §11.186(c) required bounding ALL
its possible behaviours at once rather than arguing that it probably ignores
extra lines. That makes ONE claim load-bearing above every other in this entry:

**an unsubscribed connection receives byte-identical traffic before and after.**

Measured, not asserted (g). Everything else in this entry is a consequence of
having found a way to say the first half without disturbing that.

## (b) A new verb, and why not the three cheaper options

`$DIAGON` / `$DIAGOFF`, dispatched in `computeNormalString` beside `$NOTICE`
and `$LOG` `[observed: io.cpp, computeNormalString at be2ddd81]`. Three
alternatives were weighed and are recorded because each was rejected for a
reason that could turn out to be wrong:

- **Reuse `$LOGON`** — EXCLUDED by the mandate itself (§11.186(c) item 1):
  whether masterput subscribes with it is exactly the unknowable thing, so new
  bytes on that subscription cannot be bounded. Not a judgment call, a ruling.
- **A second port** — rejected: a port is CONFIG SURFACE. It would have to be
  named in `config.ini`, told to a dome operator, and defaulted; and the
  default's value is a B28-protocol decision that is not this task's. A verb
  costs a connection that never sends it exactly nothing.
- **`$SCEDITON`** — rejected on I1: it names a CLIENT in a protocol verb, so
  any other tool wanting diagnostics would have to claim to be scedit. The
  channel is defined by what it carries, not by who was asked to listen. (The
  mandate says "dedicated for scedit"; what is dedicated is the LINK a scedit
  instance opens, not the vocabulary.)

The spelling `$DIAG` rather than `$FEEDBACK` is deliberate and it is a
readability decision, not a semantic one: the code already calls
`clientBroadcastTab` "the feedback request table" and `deliver`'s comment calls
`$LOGON` "the feedback channel". Adding a second, different thing called
"feedback" would have put two meanings on one word in one file (I2's shape at
the level of names). `clientDiagTab` sits beside `clientBroadcastTab` and the
header says at the definition why there are two tables and not one flag.

**Idempotency differs from `$LOG`, on purpose and only for the new verb.**
`$LOGON` sent twice answers `"REQUEST ERROR"`; `$DIAGON` sent twice confirms
again, because a client asking a second time wants to know the state it is in
and a re-subscription is not a fault (§2(f)). `$LOG`'s behaviour is NOT touched
— it is §5.72's row and outside this task.

## (c) The `$NOTICE` reply is NOT advertised, and that is the conservative call

`$NOTICE` still answers `"$NOTICE $LOGON $LOGOFF"`, unchanged, 24 bytes.

The argument for advertising is real: a client that asks what verbs exist and
is told an incomplete list has been lied to by omission, and discovery is what
`$NOTICE` is for. The argument against won: **that reply is bytes on
masterput's wire.** Any client that asks `$NOTICE` sees the change, and a
closed-source client may compare the reply exactly, parse it positionally, or
size a buffer from it — all unknowable, which is the same residual-information
situation the mandate ruled on for `$LOGON`. Advertising would have moved the
frozen-wire claim from "identical for a connection that did not ask for
diagnostics" to "identical unless it asks `$NOTICE`", and that weaker claim is
not the one §11.186(c) demanded.

So the verb is documented where a human or a model will actually look for it —
`util/scedit/README.md § Live mode`, the `run_command` tool description, and
this entry — and NOT on the wire. **VETO POINT**: one line in
`computeNormalString` reverses it, and the wire cost is +8 bytes on one reply
to one client that asked a question. It is Vixy's if he wants discovery over
the freeze.

## (d) The routing key is F68's origin, and three sites use it

`AppCommandInterface::sendFeedback(at, message, subject)`
`[observed: app_command_interface.cpp at be2ddd81]` sends only when
`at.channel == ScriptChannel::TCP`, and the three call sites are exactly the
three F68 mapped (§11.187(d)):

| site | what it carries |
|---|---|
| `executeCommandStatus`, the else branch | §5.117's single emitter for 157 refusals — `debug_message` + the command line |
| the emitter that BYPASSES that funnel | `"Unrecognized or malformed command name"` + the command line |
| `reportScriptError` | a structure fault + the offending line, at the origin of the line that CAUSED it |

`reportScriptError` routes on its `at` argument and not on `currentOrigin`,
which matters for the one case where they differ: an unclosed `struct if` is
reported at its OPENER (§11.184), and that opener may have arrived on a
different line from the one executing now.

HTTP routes nowhere by construction — it carries no origin at all
(§11.187(c)) — and a FILE origin routes nowhere either, which is (h)'s
boundary, not an oversight.

The record is `$DIAG|<origin>|<message>|<subject>`: engine-controlled fields
first, so the SUBJECT (a command line, which may itself contain a `|`) is last
and a reader splits at three separators. Line breaks in a composed record are
folded to spaces in `sendDiagnostic`, because one diagnostic is one record and
a client frames on them.

## (e) The same-thread contract, kept — and the one place it forced a choice

`sendDiagnostic` runs on the APPLICATION thread (it is called from the command
interface) and hands the record to the server thread through the existing
output queue, with a `diag` flag on `ClientMessage`; `checkDataToSend` routes,
and `deliverDiagnostic` reads `clientDiagTab` on the server thread — the thread
that WRITES that table in `computeNormalString`. Nothing reads the subscription
table from the application thread, so the new table needs no lock that the old
one does not have.

One queue rather than two, deliberately: a client subscribed to BOTH channels
sees answers and diagnostics in the order the application produced them.

**A record is queued even when nobody has subscribed.** The alternative —
testing "is anyone listening?" before composing — would be an application-thread
read of server-thread state, i.e. buying a few string copies with a data race.
The queue is drained on every pass of the server loop (a 1 ms
`SDLNet_CheckSockets`), so an unread diagnostic costs one string and no growth.
No warning is logged when there is no subscriber: an opt-in channel with nobody
on it is its normal state, not a fault, and the log has the line either way.

## (f) What the delivered wire does for a subscriber — 939 bytes, and what is in them

`[measured: artifacts/f69/wire.post.D.bin, f69_result.json]`. Client D sends
`$DIAGON` and receives, in order: the confirmation, then five records:

```
$DIAG|tcp#4|this 'struct if end' closes nothing: ...|struct if end
$DIAG|tcp#4|command 'get': unknown status value|get status nonsense
$DIAG|tcp#4|Unrecognized or malformed command name|flagg stars on
$DIAG|tcp#4|this 'struct if end' closes nothing: ...|struct if end
$DIAG|tcp#5|this 'struct if end' closes nothing: ...|struct if end
```

The `tcp#5` line is what makes the origin field mean the CONNECTION: a second
client's fault arrives on D's link tagged with ITS id, not D's and not P's. The
fourth line is the fault sent after `clear` nested thirty commands — the origin
survived the nesting, which is F68's RAII scope re-measured through a new
consumer.

`$DIAGOFF` is confirmed and then a further fault from P adds **0 bytes**: 870 +
69 = 939 observed. The log shows THREE faults from `tcp#4` where D's wire
carries TWO, so the leg is discriminating rather than merely quiet.

Every byte D received is ASCII (0 non-ASCII bytes measured) — but see (k):
that is a property of this battery, not a guarantee of the channel.

`f69_feedback.py` runs F68's battery with one client ADDED (D) — the sharpest

| who | bytes | pre == pre2 | pre == post | == F68's committed wire |
|---|---|---|---|---|

| the asking client P | **5** | yes | **yes** | **yes** |
| second client Q (sends only) | **0** | yes | yes | yes |
| HTTP request | **85** | yes | **yes** | **yes** |

The third column is this run's A/A control (the battery is deterministic); the
fourth is the frozen claim; the fifth compares against
`artifacts/f68/wire.pre.*` — **another task, another binary, another day**.
Three of the four are asserted NON-EMPTY, because identity over empty
recordings is a green that cannot fail. And beyond byte-identity, S is asserted
to have received no record beginning `$DIAG` at all: identity says nothing
arrived, this says the RIGHT nothing arrived.

The 71 bytes decompose exactly: the `$LOGON` confirmation (36), a copy of P's
`EOL` answer (5, §5.72's broadcast), and the HTTP `127.0.0.1/HTTP|struct if
end` line (30).

Independently, scedit's own gate proves the same boundary from the other end
against the stand-in: a `$LOGON`-only onlooker socket receives the other
client's answer and not one byte of the diagnostic channel
(`util/scedit/tests/tcp_gate.py` section I).

**THE ONE DELTA, stated because it is the complete reach of the change on an
unsubscribed connection.** A client that sends the literal string `$DIAGON` (or
`$DIAGOFF`, or anything starting with `$DIAG`) now gets a reply from the socket
layer, where before the line was pushed to the application and refused as an
unrecognised command. That is inherent to any opt-in verb — it is what "opt-in"
means — and it is bounded to clients that send that exact string. It is also
the verb's both-ways control: the PRE engine logs `Unrecognized or malformed
command name` THREE times in this battery (for `$DIAGON`, `$DIAGOFF` and
`flagg stars on`) and the delivered one logs it ONCE.

## (h) What is deliberately NOT wired, each with its reason

- **Script lifecycle events** — the mandate is feedback about TCP-origin
  COMMANDS. §11.185(d)(1)'s wider question (should the control channel carry
  lifecycle at all?) is answered only in this specific form, and the
  poll-replacement line — *"a single line on the feed at `terminateScript`
  would replace the whole poll with an event"* (§11.185(c)) — STAYS ROUTED.
  scedit's bounded file poll is unchanged and still needed.
- **Success acknowledgements** — not feedback in the ruled sense. §2(f) asks
  that a REFUSAL be actionable; it says nothing about announcing success, and
  wiring it would make silence-after-a-command mean something clients could
  come to depend on. Left unwired, stated here as the boundary.
- **File-origin refusals** — `originTag()`'s asymmetry (§11.187(d)) is
  unmoved, and this task does not widen it. A file line reports at its line and
  through the `#!` tail; whether every failing file command should also join a
  channel is the ~1661-annotations decision §11.184 left open, and taking its
  socket half here would have prejudged it.
- **NESTED refusals, and this one is a COST rather than a boundary.** A command
  the engine runs inside another (`media action play audioname nosuch.ogg` runs
  `audio filename …`) passes no origin — §11.184's rule, which F68 preserved by
  measurement — so the refusal that actually fires routes NOWHERE. A subscriber
  that sends that line is told nothing at all `[measured: leg vi-post, 0
  records mentioning audio, while the LOG carries the refusal twice]`. The gate
  asserts both halves so the silence is attributable to the channel and not to
  the run. **This is the sharpest remaining gap in the feature as delivered**
  and it is recorded, not fixed: making a nested call inherit the outer origin
  is a change to §11.184's rule, which is not this task's to make.
- **No new port, no auth work, no data writes, no `$LOGON` change.**

## (i) scedit consumes it, and two of its consumers moved because the kind moved

`TcpClient::connect` sends `$DIAGON` after `$LOGON`; `disconnect` sends
`$DIAGOFF` before `$LOGOFF`. **A `$DIAGON` failure is not fatal** — against an
engine that predates this it is an unrecognised command, and a working
connection must not be discarded because the newer half of the protocol is
absent. `FeedKind` gains `Diagnostic`, classified on the ENGINE's own `$DIAG|`
label rather than on content scedit invented; the pane draws it RED.

Adding a kind rather than a flag forced both existing consumers of `FeedKind`
to be visited, which is the point (I3): the MCP `run_command` tool would
otherwise have silently dropped every diagnostic while its `note` field went on
telling a model that *"the engine writes its refusals to its own log file,
which is not on this channel"* — true yesterday, false today. It now returns a
second list, `diagnostics`, split into origin/message/subject with the raw
record kept, and its note is COMPUTED from what arrived.

Gates, all green in `build-lovely` and in a fresh `build-f69` (0 warnings):
`tcp_client` **23/65 → 30/112**, `mcp_protocol` **77 → 85**, `ui_selftest`
**20 → 21 frames**. The ui frame is not decoration: its feed mask became
three-valued (`E`/`D`/`L`) and is read off the PIXELS, so "a refusal looks
different" is proved from the screen rather than from the `FeedKind` the
renderer was handed — the recorded mask for the new case is `feed ELDLE`, and
the seventeen non-live frames stayed byte-identical (the diff against the
previous record is purely additive, verified).

The LIVE leg rides the same launches as the frozen-wire proof: `live_diag`
against the real engine, given the OPPOSITE expectation per binary — on the
delivered one a refused command must come back split into its fields, on the
pre one it must come back as nothing. Both green
`[artifacts/f69/scedit.post.txt, scedit.pre.txt]`. The scedit half is journalled
in the mirror ledger (`claude/util/scedit/INTENT.md`, `2026-08-31i`).

The environment canary reports `xserver.restarted` on this host. F68 recorded

HOST-EVENTS at acceptance. **It is an artefact of the instrument.**
`f56_canary.sh:270` reads `stat -c %Y "/proc/<pid>"` — a directory mtime, not a
start time `[observed]`. Measured three ways on pid 14079, the Xwayland serving
`:2` `[measured: artifacts/f69/xserver-epoch-probe.txt]`:

| probe | answer |
|---|---|
| `ps -o lstart` | 2026-08-30 23:54:51 |
| `/proc/stat` btime + `/proc/<pid>/stat` field 22 / HZ | 2026-08-30 23:54:51 |
| `stat -c %Y /proc/<pid>` — what the canary reads | 2026-08-31 18:41:34 |

A pid cannot have started twice. F68's canary read ~23:54:52 for the same
process a few hours before this session's read gave 18:41:34: the mtime moved
19 hours for a process that never restarted. My own six reads across three
phases, using the btime form, are 1788126891 to the digit.

**Not fixed here, and the reason is not scope-tidiness**: `BANK_XSERVER_START`
was banked with the same wrong proxy, so correcting the computation re-bases a
banked value — a deliberate re-baselining act, and §0.5 makes re-banking one
VALUES-block edit WITH an argument. The same proxy backs
`compositor.start_epoch`, whose twin is a GATING `fail 2 compositor.restarted`:
a false red there makes an executor STOP and report a stack change that never
happened. Reported with the probe committed; the fix is one line plus a re-bank
and belongs to whoever owns the bank. **§11.187(i) is back-marked at its node.**

## (k) Costs, boundaries and adjacent facts

- **Cost** `[derived, not measured]`: one predicate per refusal of a TCP-origin
  command, plus one string copy through a queue that is drained every server
  pass. Script cadence at most, not frame cadence; no per-frame path is
  touched, so there is nothing here a 1 ms/frame budget (D11) could resolve.
  No timing claim is made. `ClientMessage` grows one bool; `ServerSocket` gains
  one `bool[maxClients]`.
- **A diagnostic's TEXT is not guaranteed ASCII.** `debug_message` reaches the
  socket, and 155 of the 157 refusal strings pass through `_()` — gettext. On
  this host the catalogue resolves to the English msgids and the whole 939-byte
  subscriber wire measured 0 non-ASCII bytes, but a French catalogue would put
  accented bytes on the wire. Every literal THIS task added is pure ASCII
  (D14); the pre-existing message catalogue is not this task's to change. **F70
  should know this is a literal-to-socket path.**
- **`app_command_interface.hpp` is ISO-8859 too** `[measured: 18 non-ASCII
  bytes, not UTF-8-decodable, present at `423cbe23~1` so not introduced by
  F68]`. CLAUDE.md and fable-dispatch §0.5 both say the `.cpp` is *"the one
  ISO-8859 file among 500 tracked `src/` files"*. A census over all 505 tracked
  regular files under `src/` finds **two**: the `.cpp` (55 bytes) and the
  `.hpp` (18). Both were patched at byte level here with the count asserted
