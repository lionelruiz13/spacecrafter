    - **(a) THE INSTRUMENT IS ITS OWN COMMIT, AND THE REASON IS THAT THE CLAIM IS PER-STEP.** `[code dc95d0de]` The parity this row asks for is not "both paths ended up turned": it is *same law, same step, same number of steps, same stop*. A `body action dual_dump` before and after a 2.5 s key hold gives two ABSOLUTE states and can say none of that — and on a binary with no mirror it cannot separate *"the ramp never reached the camera"* from *"the readout does not exist"*, which is exactly the fiction §11.132(a) caught in its own first RED half. So `Core::updateMove` now writes one `RampStep` per frame in which a ramp is active, **plus the first frame after it stops** (a key RELEASE is observed, never inferred from an absent row), carrying the frame's inputs — `delta_time`, the OLD projector's fov, the DRAWN fov authority `ModularBody::halfFov`, the scaled steps and their joypad coefficients — and BOTH paths' view parameters **before and after the step**. The ring (2048 rows, chronological, with a `dropped` count so a truncated capture says so) is dumped by `body action dual_dump` as a `"ramp"` object. The old path's half is read through the navigator's own `const` getters (`getViewingMode`/`getEquVision`/`getLocalVision`), so **no old-path source is touched at all** — the §11.130 `oldView` readback precedent, one layer smaller; the new path's half is `Camera::getViewParams()`, a `const` accessor for the two members the dump reported only at dump time. Nothing wired: behaviour unchanged by construction, and the pre-fix binary is a build of this commit (`harness/sc_f25_pre`, md5 `892328da`) so **one script measures both binaries**.
