    - **(f) FOUR DESIGN CONCLUSIONS THAT ARE NOT DECISIONS — derived from recorded authority, and load-bearing enough to state here.**
      1. **The save is a USE-SITE under D8.** §2.0 D8 lists *"any user-reachable read — draw/show, selection, save included"*; the §11.76 barrier then requires a previously-frozen body to be recomputed **+4 iterations** at the use. A save is the first consumer that touches EVERY body rather than the few in view, so the barrier's cost profile is new. A save that skips it serializes each body's staleness and makes it permanent. §5.32 is in the same path: the camera reads its reference's cached state with no drawn gate, and in a save that error does not wash out on the next frame.
      2. **§11.101(i)(3)'s clean negative is SPENT, deliberately.** The save channel was structurally clean — no jd-derived state serialized anywhere in the new path. This design serializes jd, observer position, orientation scalars and per-body overrides. Recorded as a decision so the next audit finds the decision rather than the drift.
      3. **The save must read the MODEL, never the control-surface getters.** B33/§11.108(c) measured the getter half reading the OLD path while setters are dual (heading divergent by 6.16°), and base C shows the existing config save doing exactly that — `Observer::setConf` writes the OLD observer's lat/lon/alt into `[init_location]`. A save built on that surface persists a state that was never on the dome.
      4. **The §11.66(b) annotation must go ABOVE its datum, not after it — forced by source, not preference.** The legacy loader takes the value as *the rest of the line* (`bodyParams[line.substr(0, pos-1)] = line.substr(pos+2)`, `ModularSystem.cpp:1373`) with no comment stripping, so a trailing `# …` annotation is swallowed INTO the value — inert only where the consumer is `strtod` (which is exactly why the shipped `[mimas]` trailing comment survives, §11.109(e)) and corrupting for any string-valued key. Annotate above.
      A fifth, one level down: **§5.39's parser unification is a PRECONDITION of the annotation, not a cleanup.** Only the loader knows a datum is wrong and which default it applied (§2(f)/D12), so the loader produces the annotation set and the writer consumes it; if the two read the file with different parsers they can disagree about which line a key came from and the annotation lands next to the wrong datum. §5.39 already records the unification half as decision-free; the whitespace-representability half stays suspended and is not needed.

Idempotence is a stated requirement with its own test: a file rewritten twice with the same diagnosis must be byte-identical the second time, or every save inflates the file with duplicated annotations.
