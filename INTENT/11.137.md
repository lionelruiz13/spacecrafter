# INTENT §11.137

137. **A 187 MiB derivation sat in the history for three weeks while the entry recording it stated it was uncommitted — the convention was real, its enforcement was attention (2026-08-22, Opus 5 (1M context), Vixy-directed; code `76ee38c7`, harness `ea897e1` (guard) / `4785736` (repoint) / this entry).**

Context: Vixy identified the problem structurally — *"executable ELF which is the derivation, not the origin. Either reconstructible so redundant, or non-reconstructible so unreliable anyway"* — and asked for two things, in this order: drop it from the commit, and prevent recurrence **by structure**. The second is the deliverable; the first is cleanup.

- **(a) THE FINDING, MEASURED.** `harness/sc_f24_pre` — **187 187 256 B**, ELF 64-bit, md5 `a10f1117da928e06b32d74a1cdfee7ef`, a build of code `0674d517` — tracked in HEAD and present in **46/46 commits** of `d422f3f^..HEAD`. Added by `d422f3f` (2026-08-01, F24 checkpoint 1) **beside two files that belonged**: `fable-dispatch.md` (+18/−6) and `harness/f24_b34_seams.py` (+646). That shape is the whole diagnosis — a sweep, not a decision. Four more ELFs (`sc_f25_pre` 187 302 208, `sc_f26_pre` 185 328 208, `sc_f26_child` 185 351 544, `sc_f27_pre` 187 306 688) were reachable only through `refs/original/refs/heads/CC-harness` → `df34cff`, an aborted 2026-08-07 `add -A` sync commit **whose entire content was those four binaries** [measured: `git show --stat`, 4 files, 0 insertions]. A `filter-branch` was run that day, the commit was reset away, and the backup ref was left holding 518 MiB of loose objects. The cleanup stopped one step short and nothing said so.
- **(b) THE ROOT, AND WHY IT IS NOT "SOMEONE WAS CARELESS".** The convention already existed and is stated in a dozen delivery entries — *"uncommitted per the artifacts convention"*, including **§11.132(j), the entry recording this very wave**, which lists `claude/harness/sc_f24_pre` (md5 `a10f1117`, a build of `0674d517`) among artifacts that are *"all uncommitted"*. The tree and the record disagreed for **three weeks** and no channel carried the disagreement: git validates no claim written in prose, and `git add -A` consults `.gitignore`, which did not name the file. The root is a **convention whose only enforcement was the author's attention at `git add`** — and attention is the one resource every other principle here is designed around. Root-cause depth check: correcting the commit alone leaves the class intact (the next staging binary arrives the same way), which is why the guard, not the purge, is the fix.
- **(c) THE GUARD — THREE LAYERS, EACH ASSUMING THE PREVIOUS FAILED** (`ea897e1`). **L1 `.gitignore`**: `harness/sc_f*_pre`, `harness/sc_f*_child`, `harness/spacecrafter_pre_*` — names, therefore a **proxy**; a binary under a new name walks straight past it. **L2 `githooks/pre-commit`**: content, therefore the **criterion** — ELF/PE/Mach-O/ar refused **at any size** (a 2 MiB stripped binary is as much a derivation as a 187 MiB one), plus any blob ≥ **8 MiB** (`hooks.maxBlobBytes`). The number is read off the corpus, not chosen: the largest legitimately tracked blob across both repos is **3.06 MB** (`planetsephems/vsop87.c`), the largest in the harness **1.78 MB** (a b18 PNG) ⇒ ~2.6× the real ceiling and ~12× under GitHub's 100 MiB hard rejection, so it fires **while the commit is still cheap to fix**. **L3** is that GitHub rejection — the last resort, and the expensive one: by then only a history rewrite removes it, which is exactly what this entry is paying for. `githooks/install.sh` wires `core.hooksPath` in **both** repos and then **proves the hook fires** against a throwaway index (`GIT_INDEX_FILE`, neither working tree touched): ELF refused, 9 MiB refused, **ordinary 12-byte file passed**. The negative control is load-bearing — a hook that refuses everything passes both positives and then blocks every commit in the repo. End-to-end in the lab: `git add -A` no longer sees the binary; `git add -f` + commit is **REFUSED** with the repair printed; an ordinary commit passes. **Stated limit:** git config is per-clone and is not cloned, so a **fresh clone runs no hook** until `install.sh` runs. Nothing inside a repository can close that; it is written into README next to the layout precondition rather than left to be rediscovered.
- **(d) THE PURGE IS ONE OPERATION WITH THE REPOINT, NOT TWO** (`purge-path.sh`). Shas are **load-bearing data** here: INTENT and the dispatch files cite harness commits to trace what was measured against what, and harness commit messages cite each other. Measured before touching anything: **20 distinct tokens in 14 tracked files**, **4 citations inside commit messages** (three pre-existing, one in the guard commit's own message), **0 in the code repo** (confirming supervised-by.sh's one-way-dependency measurement still holds). A rewrite that ignores them turns a traceability record into pointers at unreachable objects — silently, because git validates no sha in a message or a markdown file. So the index-filter (drop the path) and the msg-filter (remap citations of already-rewritten ancestors, via filter-branch's own map directory) run in **one pass**; a second pass would re-sha whatever the first had just repointed. Tracker files are repointed at the tip as their own reviewable commit (`4785736`), length-preserving — the length of a citation is the citing text's choice, not the tool's. Every planned substitution is printed **with its source line**, because a 7-hex token can equally be an md5 prefix and only the surrounding text discriminates.
- **(e) WHAT THE LAB REFUTED — the tool was built by failing, six times.** Every gate below exists because a scratch run tripped it, not because it was foreseen. (1) `git check-ignore` **consults the index**, so a currently-tracked path always reads "not ignored" — the ignore-coupling gate blocked every legitimate run until `--no-index`. (2) Resolving citations one token at a time is O(**269 111**) subshells on this corpus — a 2-minute timeout, replaced by a single prefix table (1.8 s). (3) `set -o pipefail` + a `grep` that legitimately matches nothing killed the run **silently**. (4) filter-branch's `map` is a shell function of **its own** shell; the shipped filter is an external script, i.e. a child process — exit 127 on the first commit. The probe that had "verified `map` is available" used an **inline** filter: it measured a different configuration than the one being shipped, and passed. (5) `$(...)` strips trailing newlines, so a remapped message came back one blank line short of every message that was not — caught byte-exact at `3f7e59b3`. (6) A `RETURN` trap in the installer outlived its function and fired in the next one under `set -u`; the harness leg had already passed when the code leg died. **And one measured surprise that changed the design:** filter-branch ends with a `reset --hard` onto the rewritten HEAD, which **deletes the purged file from the working tree**. A staging binary is a measuring instrument; silent deletion is a loss the operation was never asked to make. The copies are now saved before and restored after, md5-compared — *"the file is back"* and *"the file is the same file"* are different claims.
- **(f) THE TREE WAS NOT INERT, AND THE GATE IS WHAT CAUGHT IT.** Mid-operation the working tree went dirty: Vixy was writing `[Vixy reply]` answers into `DECISIONS_PENDING.md` (D21, D23) at 09:33. Against that tree, filter-branch's closing `reset --hard` would have **destroyed two uncommitted replies**. The clean-tree precondition refused, the rate-of-change was verified rather than assumed, and the question went back to Vixy — who committed them (`b0bebbe`) while the purge waited. Recorded because the general form is load-bearing: *a decision's time budget is set by the rate at which the state changes without one's action*, and here that rate was another agent's hand.
- **(g) THE PRUNE — the irreversible half, taken deliberately** [vixy: *"Prune now, in the same pass"*]. Ordered last, after every gate: `refs/original` deleted (the four dead ELFs' only anchor), `refs/purge-backup` deleted, reflog expired, `gc --prune=now`. **519.52 MiB loose → 88.91 MiB packed, 0 loose objects, fsck clean, 2 refs.** All five ELF blobs are gone from the object database [verified: `cat-file -e` on each]. What makes this safe is the record, not optimism: each binary's md5 and source commit are written into its delivery entry, and §11.126 already demonstrated a **bit-identical rebuild** of a staging binary from its stated commit. All five remain on disk, untouched and now ignored [verified: md5 `a10f1117…` unchanged post-run]. What is actually lost is this operation's own rollback path.
- **(h) VERIFIED AGAINST A PRISTINE BASELINE, IN A DIFFERENT REPOSITORY.** The script's own gates (per-pair tree change == the purged path only; author/committer identity and both dates; parents mapped or boundary-carried; message == the independently recomputed remap; path in no commit; blob unreachable; every citation reachable — *reachability, never existence*, since a rewrite leaves the old objects readable right up to the gc) are not self-sufficient evidence: a verifier can share a bug with the thing it verifies. So the result was re-checked **cross-repo** against a scratch clone whose `refs/original` still holds the untouched original: **44/44 trees identical modulo the removed path** (md5 of the full `ls-tree -r` listing), **44/44 author+committer identities and both dates identical**, **exactly 3 messages changed**, each one a citation whose target resolves to a commit with the **identical subject** (`56bc68b`→`37afdef`, `7385ea6`→`03cfc3e`, `d4820ea`→`a105e22`), token lengths preserved at 7. Post-repoint: **0** tracked-file tokens resolve into the pre-rewrite range, 20 resolve into the new one.
- **(i) RESIDUALS, NAMED.** (i1) The **second tree** (`/home/claude/spacecrafter (to merge with the main spacecrafter folder)/claude`) still carries the same blob across **84 commits**; deliberately not touched [vixy: *"This tree only"* — the two lines diverged at `1d4f4ca`, the merge is manual because QUEUE entry ids can conflict by design, and it is planned for its own session]. `purge-path.sh --repo=<path>` takes it unchanged when that session comes; the rewrite is deterministic, so the same paths and the same boundary produce the same shas on the shared prefix. Recorded, not acted on: each is ~1.8 MB, under the hook's ceiling, so the guard leaves them alone; whether the history should be purged of them is a separate call with its own cost. (i3) A fresh clone runs no hook until `install.sh` runs (§(c)). (i4) The code repo carries an uncommitted `debug.sh` edit, untouched.
