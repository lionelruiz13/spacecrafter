# INTENT §11.137

Added by `3003792` (2026-08-01, F24 checkpoint 1; `d422f3f` before this entry's own rewrite) **beside two files that belonged**: `fable-dispatch.md` (+18/−6) and `harness/f24_b34_seams.py` (+646). That shape is the whole diagnosis — a sweep, not a decision. Four more ELFs (`sc_f25_pre` 187 302 208, `sc_f26_pre` 185 328 208, `sc_f26_child` 185 351 544, `sc_f27_pre` 187 306 688) were reachable only through `refs/original/refs/heads/CC-harness` → `df34cff` (a sha this entry's own prune removed from existence), an aborted 2026-08-07 `add -A` sync commit **whose entire content was those four binaries** [measured: `git show --stat`, 4 files, 0 insertions]. A `filter-branch` was run that day, the commit was reset away, and the backup ref was left holding 518 MiB of loose objects. The cleanup stopped one step short and nothing said so.
- **(b) THE ROOT, AND WHY IT IS NOT "SOMEONE WAS CARELESS".** The convention already existed and is stated in a dozen delivery entries — *"uncommitted per the artifacts convention"*, including **§11.132(j), the entry recording this very wave**, which lists `claude/harness/sc_f24_pre` (md5 `a10f1117`, a build of `0674d517`) among artifacts that are *"all uncommitted"*. The tree and the record disagreed for **three weeks** and no channel carried the disagreement: git validates no claim written in prose, and `git add -A` consults `.gitignore`, which did not name the file. The root is a **convention whose only enforcement was the author's attention at `git add`** — and attention is the one resource every other principle here is designed around. Root-cause depth check: correcting the commit alone leaves the class intact (the next staging binary arrives the same way), which is why the guard, not the purge, is the fix.
- **(c) THE GUARD — THREE LAYERS, EACH ASSUMING THE PREVIOUS FAILED** (`0fc5e4e`). **L1 `.gitignore`**: `harness/sc_f*_pre`, `harness/sc_f*_child`, `harness/spacecrafter_pre_*` — names, therefore a **proxy**; a binary under a new name walks straight past it. **L2 `githooks/pre-commit`**: content, therefore the **criterion** — ELF/PE/Mach-O/ar refused **at any size** (a 2 MiB stripped binary is as much a derivation as a 187 MiB one), plus any blob ≥ **8 MiB** (`hooks.maxBlobBytes`). The number is read off the corpus, not chosen: the largest legitimately tracked blob across both repos is **3.06 MB** (`planetsephems/vsop87.c`), the largest in the harness **1.78 MB** (a b18 PNG) ⇒ ~2.6× the real ceiling and ~12× under GitHub's 100 MiB hard rejection, so it fires **while the commit is still cheap to fix**. **L3** is that GitHub rejection — the last resort, and the expensive one: by then only a history rewrite removes it, which is exactly what this entry is paying for. `githooks/install.sh` wires `core.hooksPath` in **both** repos and then **proves the hook fires** against a throwaway index (`GIT_INDEX_FILE`, neither working tree touched): ELF refused, 9 MiB refused, **ordinary 12-byte file passed**. The negative control is load-bearing — a hook that refuses everything passes both positives and then blocks every commit in the repo. End-to-end in the lab: `git add -A` no longer sees the binary; `git add -f` + commit is **REFUSED** with the repair printed; an ordinary commit passes. **Stated limit:** git config is per-clone and is not cloned, so a **fresh clone runs no hook** until `install.sh` runs. Nothing inside a repository can close that; it is written into README next to the layout precondition rather than left to be rediscovered.
- **(c1) CORRECTION, SAME DAY — THE GUARD LED WITH THE WRONG CRITERION, AND (c) IS WHAT IT REPLACED** [vixy 2026-08-22, structural]: *"no executable ELF shall ever land… instead of tracking file size, can't you track file type… what makes them unnecessary is not merely their size but the fact they are trivially reconstructible from sources and not the other way. The size is what made it visible."* **The criterion is the one-way transformation, not the byte count.** A compiled artifact is the DETERMINED end: the source determines the binary, the binary does not determine the source, because compilation destroys exactly the information that would let you go back — so of the two ends, one carries what the other cannot be recovered from, and that is the one a record keeps. Size never said any of that. It was the *visibility* mechanism — this instance announced itself at 187 MiB — and (c) mistook the thing that made the problem visible for the thing that made it a problem, which is the proxy-for-criterion substitution this architecture exists to refuse. Concretely: a 12 KiB `.pyc` is exactly as much a derivation as a 187 MiB executable **and a size ceiling never sees it**. **What changed.** `file(1)` becomes the primary channel — it reads content (names lie) and knows the shapes of compiled output far beyond the four magic numbers (c) hand-wrote: ELF, Mach-O, PE, ar, compiled Java class, byte-compiled Python, WebAssembly, core file, object/relocatable, .NET, LLVM bitcode, dex, deb, rpm. Refusal is **unconditional** — no threshold, no exemption. The magic-byte list stays as a **second channel with a different failure mode** (`file` can be absent, or reword its output between versions; the constants cannot change), OR'd, so drift between them can only widen the net — two detectors feeding one decision, which is not the two-authorities-for-one-answer duplication I2 warns about. **Size is demoted and re-reasoned rather than deleted**: reconstructibility is a SEMANTIC property — a 40 MiB capture log and a 40 MiB star catalogue are the same bytes to every detector — so the size layer now makes a *different claim*, that it has decided nothing, and hands the question to the one party who can answer it ("reconstructible → record the procedure; an origin → say so and override"). Deleting it instead would have left the harness's own likeliest future derivation — a large capture or log, no magic, no distinguishing type — with nothing but the path layer. **Measured, not asserted.** Negative control at corpus scale: the shipped hook run against **every tracked file of both repos staged as new — 3 175 files, 0 refusals**. Positive controls through the same shipped path: an **8-byte ELF refused identically to the 187 MiB one** (the size-independence the ceiling cannot demonstrate), a 16-byte Java class, and a **12-byte `.pyc` whose signature is deliberately absent from the magic-byte fallback** — that leg is the one that dies if the `file(1)` channel ever stops being consulted, which is why it is in `install.sh`'s self-test rather than in a comment. One measured detail that would have been wrong if assumed: under the bounded 8 KiB read the 187 MiB blob reports *"ELF … shared object … missing section headers"* where a full read reports *"pie executable"*, so the match is on **ELF**, never on the word *executable*. **Named blind spots**: an archive CONTAINING binaries (`.jar`, `.whl`, a build tarball) reads as "Zip archive data" and is indistinguishable from packaged source data — it falls to the size layer; and measurement artifacts (PNG, logs) are type-indistinguishable from source data, so **layer 2 (path) is the only thing standing between them and the history**. **Limit that did not change**: `--no-verify` bypasses every hook including the type refusal, and git offers no way to prevent it; the only unbypassable layer is server-side, which GitHub does not offer outside Enterprise.
- **(d) THE PURGE IS ONE OPERATION WITH THE REPOINT, NOT TWO** (`purge-path.sh`). Shas are **load-bearing data** here: INTENT and the dispatch files cite harness commits to trace what was measured against what, and harness commit messages cite each other. Measured before touching anything: **20 distinct tokens in 14 tracked files**, **4 citations inside commit messages** (three pre-existing, one in the guard commit's own message), **0 in the code repo** (confirming supervised-by.sh's one-way-dependency measurement still holds). A rewrite that ignores them turns a traceability record into pointers at unreachable objects — silently, because git validates no sha in a message or a markdown file. So the index-filter (drop the path) and the msg-filter (remap citations of already-rewritten ancestors, via filter-branch's own map directory) run in **one pass**; a second pass would re-sha whatever the first had just repointed. Tracker files are repointed at the tip as their own reviewable commit (`4785736`), length-preserving — the length of a citation is the citing text's choice, not the tool's. Every planned substitution is printed **with its source line**, because a 7-hex token can equally be an md5 prefix and only the surrounding text discriminates.
- **(e) WHAT THE LAB REFUTED — the tool was built by failing, six times.** Every gate below exists because a scratch run tripped it, not because it was foreseen. (1) `git check-ignore` **consults the index**, so a currently-tracked path always reads "not ignored" — the ignore-coupling gate blocked every legitimate run until `--no-index`. (2) Resolving citations one token at a time is O(**269 111**) subshells on this corpus — a 2-minute timeout, replaced by a single prefix table (1.8 s). (3) `set -o pipefail` + a `grep` that legitimately matches nothing killed the run **silently**. (4) filter-branch's `map` is a shell function of **its own** shell; the shipped filter is an external script, i.e. a child process — exit 127 on the first commit. The probe that had "verified `map` is available" used an **inline** filter: it measured a different configuration than the one being shipped, and passed. (5) `$(...)` strips trailing newlines, so a remapped message came back one blank line short of every message that was not — caught byte-exact at `3f7e59b3` — a pre-rewrite sha, as is every old-side sha named in this entry. (6) A `RETURN` trap in the installer outlived its function and fired in the next one under `set -u`; the harness leg had already passed when the code leg died. **And one measured surprise that changed the design:** filter-branch ends with a `reset --hard` onto the rewritten HEAD, which **deletes the purged file from the working tree**. A staging binary is a measuring instrument; silent deletion is a loss the operation was never asked to make. The copies are now saved before and restored after, md5-compared — *"the file is back"* and *"the file is the same file"* are different claims.
