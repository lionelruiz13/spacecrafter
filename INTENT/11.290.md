    ## 1. VERDICT: CAN HAPPEN, with no race needed
    The assignment can hit a joinable `thread` on one thread (the main thread), deterministically given the file's structure. There are also rarer cross-thread routes (§4).

    **What must be true beforehand:**
    - The video is wider than 1024 px. That forces `DecodePolicy::THREADED` [observed: cpp:285-286].
    - The codec gets 2 or more threads. `thread_count = codecDecodeThreads` [cpp:289-290]; on this host "50%" × 24 cores = 12 [observed: `~/.spacecrafter/config.ini:20`, cpp:101-103, `nproc` = 24].
    - FFmpeg frame threading then holds back output by thread_count−1 = 11 frames after a flush [knowledge, not checked against the installed libavcodec].
    - The file's last GOP (from the last keyframe to the end) lasts L seconds.

    **Minimal sequence:**
    1. `media action play filename X type viewport` (script, TCP or mkfifo), on the main thread. This runs `Media::playerPlay` (media.cpp:241→175) → `playNewVideo` → `threadPlay` at cpp:422, and the decoder thread starts at cpp:946.
    2. With a remaining time R where 10 s < R < 10 s + L, the operator presses RIGHT.
       - Path: `UI::handleKeysOnVideo` (ui.cpp:1022), or `speedIncrease` (ui.cpp:738) → `Media::playerJump` (media.cpp:281) → `jumpInCurrentVideo` → `seekVideo(10·fps)`.
       - Equivalent triggers: UP (+60 s, ui.cpp:1025); R, invert flow (ui.cpp:968), pressed during the first L seconds of playback; or `media action jump value J` (aci.cpp:3774) with the target inside the last GOP.
    3. `seekVideo`:
       - cpp:686 passes. cpp:696 passes: the target is before the end.
       - `threadInterrupt` (cpp:697):
         - :922 `thread` is joinable. The decoder was started in step 1 and nothing has joined it.
         - :923 bumps `frameCached` by 80.
         - :924 takes `mtx`. The decoder holds `mtx` for its whole loop except inside `cv.wait` [cpp:898]. The bump makes the wait condition at :901 true, so the decoder parks at :902 and releases the lock.
         - :925 `decoding` is true. The decoder runs at most 79 frames + 11 ahead of playback [cpp:901], and R > 10 s. So there is **no unlock and no join**: `thread` stays JOINABLE with the decoder parked.
    4. :698 seeks to the last keyframe (the seek flag at :698 is `AVSEEK_FLAG_BACKWARD`). :703 flushes the decoder. :705-706 pause. :708 sets `m_isVideoSeeking = true`.
    5. :709 `threadPlay` → :940 `getNextVideoFrame` → `getNextFrame`:
       - The keyframe packet returns no frame while the threaded decoder refills (:465-467 `continue`).
       - Later packets do return frames, but their packets are not keyframes, so they are skipped (:472-478).
       - No keyframe packet remains, so the file ends: :484 sets `decoding = false` and the read returns false.
    6. :941 is false → :945 sets `decoding = true` → **:946 `thread = std::thread(...)` while `thread` is joinable → `std::terminate()`**.

    **Consequence per the C++ standard:**
    - [knowledge] [thread.thread.assign]: `operator=(thread&&)`: "If joinable(), calls terminate()".
    - [knowledge] [terminate.handler]: the default handler calls `abort()`.
    - There is no `set_terminate` anywhere in src [observed: grep, zero hits].
    - So the process is killed (SIGABRT) in the middle of a session.

    **Where the rule breaks** [derived]: the decision at :925 ("decoder parked, lock held, not joined") and the branch at :941 read the same variable, `decoding`, at two different moments. Between them, the calling thread itself runs `getNextVideoFrame`, which can flip it to false (:484). The else branch then assumes a thread that was never joined was joined.

    ## 4. Which threads run these functions, and whether the check-then-assign window can be raced
    - **Main thread:** P1-P3, every stop call, and `~VideoPlayer` at exit (main.cpp:364 → App::~App).
    - **DrawHelper worker:** P4, plus `stopCurrentVideo(false)` at :801 → join.
    - **Decoder thread:** never touches `thread`.
    - **Serialization:** the only lock shared by the main thread and the DrawHelper worker on these paths is `videoTransitionMutex`, and only inside `stopCurrentVideo` (:527). Interrupt, play, restart and seek are unserialized. `mtx` serializes only interrupts of kind (C).
    - **They really overlap:** `recordUpdate` for frame N runs while the main thread goes on from `submitFrame` (app.cpp:893), through input handling and `update` of the next iteration (:979-1000), up to `waitFrame` (:801) [observed]. The overlap goes away only with `flushFrames` (:897-900), a diagnostic mode (:209-210).
    - **So the window can be raced (timing-dependent, milliseconds wide, not measured):**
      - **X1, assignment on a joinable thread across threads.** A looped video reaches its end. The DrawHelper thread restarts it (:798): its interrupt joins at :927. Meanwhile the operator's restart or seek on the main thread sees `joinable()` false at :922.
        - Both threads then run `getNextVideoFrame` on the same FFmpeg contexts. That is undefined behaviour [knowledge].
        - The first to reach :945 assigns. The second, if it read `decoding` before that store, assigns over a now-joinable thread → terminate.
        - Otherwise it takes the other branch and runs `mtx.unlock()` on a mutex it does not own → undefined behaviour [knowledge: thread.mutex.requirements].
      - **X2, double join.** The DrawHelper thread stops the video at end of file (`threadTerminate`). The main thread's `seekVideo` read the plain bool `m_isVideoPlayed` before :531 (a data race) and its interrupt passes :922.
        - Two concurrent joins → undefined behaviour.
        - If they come one after the other, the second join on a non-joinable thread throws `system_error(invalid_argument)` [knowledge: thread.thread.member]. Nothing catches it → terminate.
        - The main thread also then uses FFmpeg contexts freed at :554-559.
      - X1-type interleavings also exist between a DrawHelper restart or stop and a main-thread `playNewVideo`, since the restart does not take `videoTransitionMutex`.

    ## 5. Other failures on the same member
    - **Join on a non-joinable thread:** impossible on one thread, because both joins are guarded (:908/:914, :922/:927). Possible across threads (X2).
    - **A thread joining itself:** impossible. Only the decoder thread is ever held in `thread`, and it calls no join [observed]. `resource_deadlock_would_occur` cannot happen.
    - **H1, a join that never returns (created by `20ad3ef5`):**
      - The bump at :923 lands while the decoder is in its final call, the one that reaches end of file.
      - The decoder stores false at :484, then evaluates :901 against the bumped counter. The `&& decoding` guard was removed, so it parks at :902.
      - The caller takes the lock at :924, sees `decoding` false at :925, and joins at :927.
      - Nobody notifies, and the wait condition stays true until :930-931, which run only after the join. Result: the main thread (or the DrawHelper thread) hangs.
      - The window is the duration of the decoder's last call. Rare.
    - **H2 (also created by `20ad3ef5`), a narrower variant:**
      - `threadTerminate` sets `frameCached = frameUsed` at :911.
      - A concurrent `frameUsed` increment on the DrawHelper thread (:764 after its load at :760, or :740) lands before the decoder re-checks.
      - The unsigned subtraction underflows, :901 becomes true, and the decoder parks again. The DrawHelper thread now returns early at :719, so no further notify comes, and the join at :914 hangs.
    - **Destructor leaving `thread` joinable: that failure is never reached; a null dereference fires first.**
      - `~VideoPlayer` sets `media = nullptr` (:114), then calls `stopCurrentVideo(false)`. If a video is playing, :532 `media->textDel` runs on a null pointer → SIGSEGV before `threadTerminate` (:542), with the decoder still joinable.
      - Reachable: `shutdown action now` (aci.cpp:2270) or SIGTERM (signals.cpp:66) during playback. Nothing on the exit path stops the player; the only `playerStop` callers are app.cpp:650 at init, aci.cpp:3768, ui.cpp:960/965 and media.cpp:225 [observed: grep].
      - The DrawHelper thread is already stopped at app.cpp:216.
      - Origin: `049bf329` (2022) nulled `media` so that the old `if (media)` guard would skip the callbacks. `9646b44d` (2025-06-14) moved the callbacks out of that guard [observed: git show]. The requirement the guard encoded was dropped.
      - If a video is not playing, the early return is safe under rule R.
