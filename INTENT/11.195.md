## (a) The chain, link by link — and the two links that could have broken it

Every citation is at `9a3b7a55` (the pre-fix HEAD) unless said otherwise.

1. **The script line.** `set sky_locale zh_CN` — `m_set["sky_locale"] =
   SCD_NAMES::APP_SKY_LOCALE` `[observed: app_command_init.cpp:319 with
   ACP_SC_SKY_LOCALE at base_command_interface.hpp:568]`; `parseCommandSet`
   is the lookup `[observed: app_command_interface.cpp:2290-2302]`;
   `evalCommandSet` dispatches `stcore->setSkyLanguage(setValue)` — **the value
   is not validated anywhere on the way** `[observed: :2349]`.
2. **One guard on the path, and it is a liveness guard.**
   `Core::setSkyLanguage` returns early `if (!hip_stars || !cardinals_points ||
   !asterisms || !skyLineMgr->isExist(SKYLINE_TYPE::LINE_ECLIPTIC))` —
   *"objects not initialized yet"* `[observed: core.cpp:1576-1578]`. In a
   running engine it is passed by construction: the same four objects are what
   the rest of the function translates.
3. **First link that could have broken the chain — and did not.** The branch
   does not test the script's argument, it tests
   `skyTranslator.getLocaleName()` `[observed: core.cpp:1588-1589]`, and
   `Translator`'s own header promises *"If the passed locale name cannot be
   handled by the system, default value will be used"* `[observed:
   translator.hpp:46-47]`. Had that been true, `zh_CN` on a host without that
   locale would never reach the branch and this defect would be conditional on
   the installation. **It is not true.** `langName` is member-initialised from
   the argument and never assigned again — the only three occurrences in the
   translation unit are that initialiser, a filename concatenation and a
   commented-out trace `[observed: translator.cpp:49-50, :89, :90]`;
   `reload()` opens `moDirectory+langName+".txt"` and, if the file is absent,
   simply does nothing `[observed: :80-119]`; `getLocaleName` returns the
   member `[observed: translator.hpp:62-64]`. **The branch condition is the
   script's own string, character for character**, on every host, installed
   locale or not.
4. **The call.** `language[0]=='z' && language[1]=='h'` →
   `fontFactory->updateAllFont("/home/planetarium/.spacecrafter/fonts/HanWangHeiHeavy.ttf")`
   `[observed: core.cpp:1589-1590]`; `ja` is the second door `[:1591-1592]`.
   (`language[0]` on an empty string is defined since C++11 and returns `'\0'`,
   so an empty locale takes the `else` branch rather than faulting.)
5. **The container states, from the code that fills them.** `updateAllFont`
   iterates **all ten** keys of `m_strToTarget` `[observed: fontFactory.cpp:43-52,
   the ten `TF_*` strings at base_command_interface.hpp:684-693]` and searches
   `listFont`, which `init()` fills with **exactly nine** `FontContener`s
   `[observed: :91-131]`. The nine map values pair one-to-one with the nine
   pushed classes (`planets`→SSYSTEM, `constellations`→ASTERIMS,
   `cardinal_points`→CARDINALS, `stars`→HIPSTARS, `menu`→UI,
   `nebulae`→NEBULAE, `grids`→SKYGRID, `lines`→SKYLINE, `displays`→SKYDISPLAY);
   the tenth, `text`→`CLASS_MENU`, has no container — it is Media's font,
   reached by `updateFont`'s special case instead `[observed: :156-159]`.
6. **Second link, and this is the one that makes the reachability STRUCTURAL
   rather than circumstantial.** The class set of `listFont` is
   **input-independent**: the nine `CLASSEFONT` arguments are literals in
   `init()`, `push_back` on `listFont` appears nowhere else, and `listFont` is
   private with no friend and is named in no other translation unit `[measured:
   grep over `src/` — every `listFont` occurrence is inside
   `fontFactory.{hpp,cpp}`]`. **No configuration, no data file and no other code
   path can put a `CLASS_MENU` container in that list.** The search for it
   therefore cannot succeed — not "does not happen to succeed here", cannot.
7. **Order, which decides the blast radius.** `std::map` keeps its keys sorted,
   so the loop visits `cardinal_points, constellations, displays, grids, lines,
   menu, nebulae, planets, stars, text` — **`text` is LAST** `[measured:
   f74_repro plain run, nine `rebuild` lines then the fault]`. The nine
   iterations that work all run before the one that cannot.
8. **What the dereference reads.** `float size = it2->fontPtr->getFontSize();`
   with `it2 == end()` `[observed: :176-177]`. `sizeof(std::list<FontContener>)
   = 24` and `offsetof(FontContener, fontPtr) = 8` `[measured: f74_repro layout
   probe]`, so `it2->fontPtr` reads 24 bytes past the list header — which is
   `FontFactory`'s **next member**, `std::string FontFileNameText`
   `[observed: fontFactory.hpp:109-112]`, whose first eight bytes are its data
   pointer. That pointer is then used as an `s_font*`. **Measured, not
   derived**: UBSan dumps the object it was asked to call through and the bytes
   are `2f 68 6f 6d 65 2f 63 6c 61 75 64 65 2f 2e 73 70 61 63 65 63 72 61 66 74
   65 72 2f 66` — `/home/claude/.spacecrafter/f…`, the text font's path.

**A second door to the same line, not through a script**: `Core::init` reads
`[localization] sky_locale` from `config.ini` and calls the same function
`[observed: core.cpp:510-512]`, so a field install with `sky_locale = zh_CN`
reaches the dereference at startup. Not exercised here (the liveness guard of
link 2 at that point in initialisation is unverified); recorded because it
means the script surface is not the only reach.

## (b) The demonstration: three instruments that could each have refuted it

The engine was **not** launched. A full ASan engine build was judged
disproportionate for one line (whole-tree rebuild, Vulkan under ASan, the
launch discipline of §0.5) and the dispatch sanctioned the alternative
explicitly. `claude/harness/f74_repro/` compiles the **real**
`src/appModule/fontFactory.{hpp,cpp}` — not a transcription — against a stub
tree supplying only `s_font`, `InitParser`, `AppSettings`, `cLog`, `Utility`
and `Media`, and replays the two engine sequences that bracket the fault:
`App::firstInit`'s `init`/`initMediaFont`/`buildAllFont`/`registerFont`
`[observed: app.cpp:701-705]` and the `zh` branch's single call.

**Why this preserves the question** (the thing a stub harness could destroy):
the reachability claim is entirely about which `CLASSEFONT` values are in
`listFont` versus which are in `m_strToTarget`, and both sets are produced
**by the real code** — `init()`'s nine literal `push_back`s and
`setStrToTarget()`'s ten literal keys, with the real `TF_*` macro strings from
the real `base_command_interface.hpp`. The stubs decide what a font *does*, the
`[font]` values (taken from this host's live `config.ini`, giving
`fontFactor = sqrt(1024/1024) = 1`) and where a log line goes — none of which
can add or remove a container. Per (a)6 the class set is input-independent, so
there is no stub choice that could have made `find_if` succeed.

| configuration | pre-fix (`9a3b7a55`) | post-fix (`54a2b844`) |
|---|---|---|
| plain `-O0` | **survives**: nine rebuilds, then `media->updateTextFont(6.74291e+22, HanWang…)` — rc 0 | nine rebuilds, one warning, rc 0 |
| `-D_GLIBCXX_DEBUG` | **`Error: attempt to dereference a past-the-end iterator`**, `state = past-the-end`, `_Sequence = std::debug::list<FontContener>` — abort, **rc 134** | no report, rc 0 |
| `-fsanitize=undefined` | **`fontFactory.cpp:177:41: runtime error: member call on address … which does not point to an object of type 's_font'`** + the object dump of (a)8 | no report, rc 0 |
| `-fsanitize=address` | **silent**, rc 0 | silent, rc 0 |

Checked libstdc++ names the fault in the language's own words, at the iterator
that is the subject of §5.119's claim; UBSan puts it at **line 177, column 41**
— the exact expression — and prints the sibling member it landed in. Both
detectors are silent on the fixed code. The plain configuration answers the
question §5.119 left owed (*"whether it crashes, reads garbage, or survives by
luck"*): **it survives by luck, and hands `6.74291e+22` to the text font**,
reproducibly (same value across four runs — the bytes are deterministic).

**ASan's silence is expected and is an instrument fact worth keeping**: this is
an *intra-object* overflow (the read stays inside the `FontFactory` allocation)
followed by a member read at a small offset inside the string's own heap buffer.
ASan has no redzone between two members of one object. In the shipped engine the
second read would be far deeper — the real `s_font::fontSize` sits behind a
vptr, a render cache and an iterator `[observed: s_font.hpp:73-113]` — so a
full-engine ASan build would likely report a heap-buffer-overflow there; that is
**[derived]**, and it is the one claim in this entry no instrument here made.

## (d) The one new line stands on a path that had no behaviour to preserve

Pre-fix, *if* the dereference happened not to fault, the run continued into
`updateFont("text", …)` → `media->updateTextFont(size, fontName)` with a size
taken from memory that was never a size (`6.74291e+22` here). Post-fix that call
does not happen and a warning is written. **This is an acting default and it is
logged (D12), and it is also the point where no behaviour-preservation claim can
be made in either direction: undefined behaviour has no defined behaviour to
preserve**, so "the text font is no longer rebuilt on a Chinese locale switch"
is not a regression against a specification — there was none — and the log line
is not a new line on a defined path. Saying which of the two it is, is exactly
the choice (e)1 keeps with its owner.

The line's content follows §2(f)/D12 as refined at §11.169 — CAUSE (*target X
has no font container*), CONTENT (*its font is left unchanged*), SELF-CONTAINED
ACTION (*set it with `font target X filename <file.ttf>`* — the shipped command,
`[observed: app_command_interface.cpp:4330-4338]` with `W_TARGET`/`W_FILENAME`
at base_command_interface.hpp:123,79). Severity `L_WARNING`, which is what both
neighbours use for the same class of miss.

## (e) Judgment calls, each with its argument

1. **Skip, rather than route `CLASS_MENU` to `media->updateTextFont`.** §5.119
   framed this as the real question and it survives the fix untouched: *what
   should a Chinese or Japanese locale switch do to the text font?* Routing it
   would need a size, and every candidate size is invented (the read that used
   to supply one was the bug). Inventing one is a behaviour choice —
   the owner's second condition forbids exactly that. **The question is
   restated at §5.119's node, not answered here.**
2. **No `assert(0)`, though both neighbours have one.** Their else branches
   guard can't-happens: `updateFont`'s is unreachable because `CLASS_MENU`
   returns earlier and the other nine targets are all in the list, and
   `registerFont` is called from thirteen sites, every one of them with a class
   that is in the list and none with `CLASS_MENU` `[measured: grep
   `registerFont(CLASSEFONT` over `src/` — app.cpp:705 and core.cpp:191-204]`.
   **This branch is the opposite: it is reached on every zh/ja locale switch.**
   Copying the neighbour form completely would put an abort on a path that is
   taken — a behaviour change well beyond removing the UB access — and in the
   shipped configuration it would not even be that, since `CMAKE_CXX_FLAGS_RELEASE`
   carries `-DNDEBUG` `[observed: build-claude/CMakeCache.txt]` and both existing
   asserts are already no-ops there. Deviation from the reference form, taken
   deliberately, recorded here for veto.
3. **No engine launch.** Proportionality (b), plus: a launch would answer *what
   the field binary does with `6.74e22`*, which is a question about a defect
   now removed. What it would NOT add is reachability — the repro runs the same
   code over the same container states. Flagged rather than absorbed: if the
   owner wants the field consequence on record, one scripted launch on the pre
   binary is the measurement, and it is not made here.
4. **The rider left alone.** `core.cpp:1590/1592` hardcode
   `/home/planetarium/.spacecrafter/fonts/…` where every sibling composes
   `AppSettings::getUserFontDir()` — so on this host the nine fonts are rebuilt
   from a path that does not exist. Out of scope (one function's guard), still
   recorded at §5.119's node, and now with an observation attached: the nine
   rebuild calls happen regardless, so whatever `s_font::rebuild` does with a
   missing file, it does it nine times per zh/ja switch.

## (f) Found en route and MINTED: §5.121 — one translation table for two locales

Verifying link 3 meant reading `Translator`, and the reading turned up a defect
of a different mechanism, reachable from the shipped script surface with
consequence (§5.79): **`m_translator` is a `static` map shared by every
`Translator` instance** `[observed: translator.cpp:40]`, filled **only** from
the constructor's `reload()` `[observed: :49-53, :80-119]`, and the tree has
exactly two instances — `Translator::globalTranslator` (the UI's, behind `_()`)
and `Core::skyTranslator` `[measured: grep — translator.cpp:43, core.cpp:85,
:1585, app.cpp:937 are all four constructions in `src/`]`. Whichever was
constructed last owns the table for **both**. Minted with its riders (the
header's false fallback promise; a missing locale file that produces no
diagnostic at all; and `lastUsed`, an identity test against a pointer that
dangles after every reassignment) at §5.121 — READ, NOT RUN, with the
measurement it needs named in the row.
