    - **(a) THE STRUCTURAL ANSWER: an anchor is a place, and a place in this engine is a body.** The new-path Camera anchors to a `ModularBody` and parametrizes its pose as (lon, lat, distance) in that body's frame [observed: `Camera.cpp:463-476`]. So the two POSITIONAL kinds are expressed by giving the camera a body to reference, and nothing in `CameraAnchors` computes a position: an ON_ORBIT anchor OWNS a hidden `ModularBody` carrying the authored orbit under `parent=`, a FIXED_POINT anchor owns one parked at a `still_orbit` offset from the tree root. Ephemeris evaluation, parent-frame accumulation, reference-switch compensation, lifetime and destruction-notification are all the tree's already (I2 — the alternative, an anchor-local position type, would have been a second authority for "where is this point at date jd", i.e. the old path's `AnchorPointOrbit::update` re-implemented beside the one the bodies use). The kind that is NOT a place — ATTACHED — creates no body: it names an existing one.

    - **(b) KIND (3) ON_ORBIT — `type = orbit`, the PRIMARY [R3].** Parent from `parent = <body>`; the orbit from the anchor's own `coord_func` + `orbit_*` keys, which are the SAME keys the body loaders read, so `ModuleLoaderMgr::loadOrbit` is the single orbit authority for anchors and bodies alike. **The parentless `orbit_center_x/y/z` form of the old grammar is PRESERVED, not retired** (the requirement it serves: *an orbit centred on a place rather than on a body* — the shipped `orbit_autour_point` uses it): the centre becomes an implicit fixed-point anchor body and the orbiting anchor is its child, so there is still only one notion of "orbit centre".

    - **(c) KIND (2) ATTACHED KEEPING THE ANGLE — `type = body` + `follow_rotation = false`, R3's NEEDED GAP.** *"Keeping its angle to the planet"* is implemented as `Camera::setBoundToSurface(false)`: the camera's lat/lon are then held in the body's ACCUMULATED EQUATORIAL frame, with no surface fold, so the body spins under a viewpoint whose direction is fixed [observed: `Camera.cpp:87-94`, `:475-476`]. The two legs are the in-run discriminator — same binary, same scene, same instrument, 87.72 deg apart.
      **`follow_rotation` ABSENT is INACTION**: the camera's bind state is left untouched, so every pre-existing scene is bit-unchanged and there is **no acting default to log** (D12; the D18 *"inaction is no rotation"* precedent).     - **(d) KIND (1) FIXED_POINT — `type = point` | `type = observatory`, Universe-scoped.** R3: *"only useful in the Universe mode… nothing moves there"*. The coordinates are therefore read in the **ROOT (Universe) frame** — the one frame in which a fixed point is fixed — and the anchor body is parked there. **The out-of-Universe behaviour is DEFINED and LOGGED (D12): the switch SUCCEEDS and moves the camera's reference to the universe frame, rather than refusing.** Reason: on the new path the reference chain IS the mode (§6.9 — modes are emergent from nesting), so "valid only in Universe mode" is realized by where the anchor LIVES, not by a mode test that would have to invent one; and a refusal mid-show is a harder failure than a documented reframing. The log line names the frame and how to get back.

    - **(f) TWO PRECONDITION DEFECTS THE KINDS EXPOSED, both fixed at the class (I6).**

    - **(g) LIFETIME (I5) AND THE RELOAD PATH.** The registry holds `ModularBodyPtr`, and liveness is asked of the **name registry**, never of the pointer: a destroyed body's remnant pointers are REDIRECTED TO ITS PARENT (`ModularBodyPtr::redirect`, the A9/R2 fallback), so *"not null"* is not *"alive"* — an anchor whose body a `body action reload` destroyed would otherwise silently become an anchor on the Moon.
