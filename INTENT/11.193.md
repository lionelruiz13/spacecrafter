## (a) The owner's model, extracted from the statement

One error RENDERING exists per faulty line: the line as it reads in the
file — author comments included, so the line is unambiguous — with the
machine's ` #! <message>` tail appended: the **intent-modified line**. That
rendering is the single authority for how this error looks (I2), and every
sink shows IT:

- the FILE, when the annotation lands (the §11.184 writer);
- the LOG, always — prefixed with the origin (his example: `Error executing
  <file>:5: get status nonsense #! <message>`), so the log line is
  self-sufficient (§11.169) AND matches what the user finds when they open
  the file at that line — *"emergent resolution"*: the two views cannot
  disagree because they are one rendering;
- and when the file is READ-ONLY, the log STILL shows the intent-modified
  line *"even if the modification never lands there"* — which is the clause
  that carries the structural key: **the rendering exists independently of
  the write**. Landing it in the file is a separate, permission- and
  ruling-gated act.

Extraction — **it supplies what our I7 rule lacks: the STANDPOINT.**

1. The error's responsibility anchor = its I2 placement (highest
   hierarchical level where it is unique and useful); in EXECUTION space
   that maps to the EARLIEST point — detection.
2. The FORM is owned at the anchor — one rendering, decided where the
   information is born, routed down. Sinks never re-render (why
   one-renderer/many-sinks was immediate from the owner's side).
3. Channel enumeration is performed AT the anchor, where it is complete BY
   TOPOLOGY — every consumer is an out-edge of one node. From a sink's
   position (where we stood at §11.184, building the file writer), sibling
   channels are invisible and enumeration degrades to RECALL — which is
   exactly how the log channel was missed. I7 says "enumerate the
   channels"; this says WHERE TO STAND so the enumeration cannot be
   incomplete. It closes a triangle: I2 places the anchor, I3 makes the
   anchor the notifier (push from detection), I7's equivalence must hold
   over the anchor's out-edges.
4. Held ABSTRACT (implementation-free) the view is a SPECIFICATION (I1) —
   stable across implementation churn, every consequence re-derivable,
   which is what made the owner's formation-time expectation testable
   rather than post-hoc.

**Process change adopted (veto-open): §0.5 gains the anchor-first bullet
(same commit)** — any task that creates or reroutes an information event
names the event's anchor and walks its channels FROM it, in the section,
before implementation. F73's acceptance will check the renderer is
anchored once — a future third sink must hook the ANCHOR, not a sink.
