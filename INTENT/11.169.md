# §11.169 — THE LOG-CONTENT SCHEMA TRANSMITTED: D12's acting defaults and §2(f)'s diagnostics gain their required log-line ELEMENTS (2026-08-30, Claude Fable 5, supervising session 16; RECORD-ONLY — in-conversation Vixy transmission at round open)

**(a) The transmission, verbatim [vixy: 2026-08-30, in-conversation, prefixed *"Informations I might have forgot to transmit"* — the prefix itself declares expected partial overlap with what is already recorded]:**

> *"each proactive decision taken by the software must be logged with what caused the implicit decision to be necessary (ex: a field set to an invalid value), what is the implicit decision (what is decided implicitly) and which action a user reading this should take in order to define/override it explicitly. For an error, what is the error, what are the consequences of the error, and which action a user reading this should take in order for it not to happens (at least for user-facing error like scripts or datas). The "which action a user readong* [sic] *this should take" shall be self-contained, not requiring deep understanding of the whole system (a field set to invalid value must enumerate the valid values, or their shape if not enumerable)."*

**(b) What it refines [derived — element-by-element delta against the constraint text at harness `ea30749`; the delta analysis is mine, the elements are Vixy's]:** this is a REFINEMENT of §2.0 D12 + §2(f), not a new constraint — it specifies the required CONTENT of the log lines those two constraints mandate.

- **Implicit-decision schema (D12's acting defaults).** Three required elements per logged proactive decision:
  1. **CAUSE** — what made the implicit decision necessary (Vixy's example: a field set to an invalid value);
  2. **CONTENT** — what is decided implicitly;
  3. **OVERRIDE** — which action a user reading the log takes to define/override the decision explicitly.
  Elements 1–2 were already carried by D12's composition with §2(f) (*"the log line names what fired and why"*, fallback stated). Element 3 is **NEW at D12**: the log must teach the reader how to make the implicit decision explicit, not only that it was taken and why. D12's log stops being a notification and becomes a handle.

- **Error schema (§2(f)).** Three required elements per user-facing error:
  1. **WHAT** — what the error is;
  2. **CONSEQUENCES** — what follows from the error;
  3. **PREVENTION** — which action the reading user takes so it does not happen (again).
  §2(f) already carries element 1 plus a resolution-action and the fallback statement. Element 2 — CONSEQUENCES — is **NEW**: nothing in §2(f) asks the diagnostic to state what the error costs downstream. Element 3 shifts the action's framing from resolution (*"which actions to take in order to resolve"*) to **prevention** (*"in order for it not to happens"*) — a superset: prevention includes resolution plus non-recurrence. **Scope floor stated**: *"at least for user-facing error like scripts or datas"* — the mandatory scope is user-facing surfaces (script errors, data errors); wider application is unforbidden, not required.

- **Self-containment criterion (binds the action element of BOTH schemas).** The "which action a user reading this should take" element must be self-contained — usable *"not requiring deep understanding of the whole system"*. Operational test given: **a field set to an invalid value must enumerate the valid values, or their SHAPE if not enumerable.** §2(f)'s existing *"an arbitrary user looking at it could understand which actions to take"* pointed here; the shape-when-not-enumerable clause is **NEW** and closes the case §2(f) left open (a value space too large to enumerate still owes its grammar).

- **The example's double face [derived]:** an invalid field value produces BOTH records when the software proceeds — an error record (what/consequences/prevention) AND an implicit-decision record (cause/content/override) for the fallback it acted on. §2(f) already fused these (*"traces it as an error, and states what it fell back to"*); the refinement gives each half its full schema. One log entry carrying all elements satisfies both — nothing here mandates two lines.

**(c) Reach [derived]:** applies to every NEW diagnostic and acting-default surface from here on (§2(f)'s own applicability clause carries this forward), and to the diagnostic ARM of every open fix fork the ledger holds — first clients when their forks are decided: **§5.110** (its three-contract fork includes a §2(f)-diagnostic option — that option now owes cause/content/override, and note §11.166(f) already measured that a diagnostic alone cannot restore discriminability there), **§5.113** (the fail-loudly class decision — a loud failure per this schema states what was not selected, what the command would have acted on, and how to select explicitly), **§5.88** (the caller-checks contract is the only fork arm holding both the file name and the config key — exactly the self-containment criterion acting as a fork discriminant), **B28's loader validation** (§2(f)'s named first client — frame/enum validation must enumerate valid frames/enums; it already was built to §2(f), so the delta to audit is CONSEQUENCES + OVERRIDE). **Named as a queue candidate, not run:** an audit of EXISTING shipped diagnostic/acting-default surfaces against the two schemas (which log sites carry which elements; the gap list is the fix's work order).
