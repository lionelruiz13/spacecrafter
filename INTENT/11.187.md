## (a) What this adds to §11.184, exactly

§11.184 built the file half and stopped at a recorded boundary: *"the
two-argument overloads — TCP/HTTP/UI, `clear`/`media`/`lift_off` nesting —
pass none: log-only"*. The mandate names **tcp** as an origin a command must

members. TCP now carries an origin; HTTP and UI still pass none, and NESTING
still passes none — that last one is not a leftover but the rule, re-measured

## (b) The contract, written in the header before the code

`src/scriptModule/script_origin.hpp` `[observed: :29-116 at 423cbe23]`:

- `enum class ScriptChannel { NONE, FILE, TCP }` — the two the mandate names,
  plus the honest zero. NONE is not "unknown": it is *this producer has no
  channel identity to give* (the UI, a joypad, the mkfifo pipe, an HTTP query,
  an engine-synthesised splice, a nested call).
- `ScriptOrigin` gains `channel` and `connection`; `file`/`line`/`text` are
  untouched. `connection` is the **never-reused** id `ServerSocket` hands a
  slot (`clientIdTab`), not the slot number — a slot is reused, so the id is
  what makes a later answer follow the connection that asked rather than
  whoever holds its slot now (I5; §5.47's own argument, now serving a second
  consumer).
- **`valid()` does not widen.** It was *"a file line the annotator may write
  into"* and it still is; it now says so in its own text
  (`channel == FILE && !file.empty() && line != 0`). The `#!` writer
  (`ScriptAnnotator::note`, ignores an invalid origin) is unmoved by
  construction: a TCP origin does not widen its gate, it fails it.
- `where()` answers the OTHER question — *does this diagnostic name where it
  came from* — with `"file:line"`, `"tcp#<id>"`, or `""`. The header states
  which consumer may ask which: a reader that wants to WRITE asks `valid()`, a
  reader that wants to NAME asks `where()`. Keeping one predicate for both
  questions is how `valid()` would have widened by accident.
- `channel` is the **first** member on purpose: the one aggregate
  initialisation that existed for the three-field struct
  (`ScriptOrigin{file, lineNo, line}`, script.cpp:119) no longer compiles, so
  a producer written before the channel existed is a build error rather than a
  line that silently claims to come from nowhere. It was replaced by the named
  factory `ScriptOrigin::fromFile` `[observed: script.cpp:119]`; `fromTcp` is
  its twin.

## (c) The socket layer says what only it knows — and the door nobody had named

`ServerSocket` already latched the serving connection for `setOutput` (§5.47);
this publishes it: `servingConnection()` and `servingIsHttp()`
`[observed: io.hpp:137, :141]`, read on the same thread as `getInput` by the
same argument the header already made. `App::updateFromSharedData` turns them
into the command's origin `[observed: app.cpp:765-785]`.

**The near-miss worth recording**: an HTTP `?command=` query is pushed into the
*same input queue* as a control line `[observed: io.cpp:596, computeHttp]`, and
its connection is CLOSED before the application ever sees the command. Taking
`servingConnection()` alone would therefore have labelled every HTTP query
`tcp#<id>` — a FALSE provenance claim, and a worse failure than the missing one
the mandate is about. `ClientMessage` gained one `bool http`
`[observed: io.hpp:103]`, `pushRequest` one defaulted parameter, and the drain
maps HTTP to **no origin at all** — which is exactly what HTTP had before, so
nothing about HTTP behaviour changes. Wiring HTTP as its own channel is a
one-line change at `app.cpp:777` once somebody wants it; it is NOT taken here
(the mandate names file and tcp, and the task's boundary says mapped, not
wired). Measured, not argued: leg (ii) row 4.

## (d) Where a diagnostic names its origin, and where it deliberately does not

- `reportScriptError` names both channels through the one accessor
  `[observed: app_command_interface.cpp:219]`: a TCP-origin structure fault
  logs `script tcp#3: <what> [<the line>]` exactly as a file one logs
  `script <file>:<line>: <what> [<the line>]` (§11.184's shape).
- The funnel `executeCommandStatus` — §5.117's single emitter for 157 refusals
  — prefixes BOTH of its lines with `originTag()`
  `[observed: :1270-1272]`, and the emitter that BYPASSES it (unrecognised
  command name) does too `[observed: :327]`.
- `originTag()` `[observed: :232-246]` returns non-empty for **TCP only**.
  **This asymmetry is a decision, and it is Vixy's to reverse in one
  condition.** The reading behind it: a file line already has a channel that
  reports AT the line (`reportScriptError` + the `#!` tail), and whether every
  failing command joins that channel is the ~1661-annotations-into-35-shipped-
  scripts decision §11.184 disclosed and left open — it is not this task's to
  take, and taking its LOG half alone would prejudge it while changing the
  shape of every file script's refusal lines. The other reading is real: a
  file-origin refusal line naming `<file>:<line>` costs nothing and helps a
  reader, and the log is not the script. Both recorded; the code says which
  and why at the definition; the reversal is `channel != TCP` → `channel ==
  NONE`.
- §5.117's severity claim is untouched (every line stays at `L_DEBUG` in
  `LOG_FILE::SCRIPT`) and its row is annotated at its node: its cited emitter
  now carries an origin tag for TCP origins, and its line numbers moved (below).

## (e) The producer map — every way a command enters the engine, wired or not

| producer | entry point (at 423cbe23) | origin today |
|---|---|---|
| script FILE | `Script::load` → `Token` → `ScriptMgr` `[script.cpp:119; script_mgr.cpp:315, :338]` | **FILE** + path + line (§11.184) |

The identical fault (`struct if end`, nothing open), five ways, one run

| sent by | post | pre |
|---|---|---|
| client P, cold | `script tcp#3: … [struct if end]` | `script: …` |
| client P, right after `clear` (thirty nested commands) | `script tcp#3: …` | `script: …` |
| client **Q**, a second connection | `script tcp#4: …` | `script: …` |

## (g) The wire, frozen — and it is F69's baseline

§11.186(c)'s hard boundary: an unsubscribed connection must see BYTE-IDENTICAL
traffic. Every byte received by a `$LOGON` subscriber, by two plain clients and
by the HTTP request is recorded per phase and committed
(`artifacts/f68/wire.<phase>.<who>.bin`):

| who | bytes | pre == pre2 | pre == post |
|---|---|---|---|
| `$LOGON` subscriber | 71 | yes | **yes** |
| the asking client | 5 | yes | **yes** |
| HTTP request | 85 | yes | **yes** |
| second client (sends only) | **0** | yes | yes |

The subscriber's 71 bytes are the `$LOGON` confirmation, a copy of the other
client's `EOL` answer (§5.72's broadcast, live again) and the HTTP
`127.0.0.1/HTTP|struct if end` line; the asking client's 5 are its own
`EOL\n\0`. The second client's **0** is not evidence of anything — it is
§11.185(a) measured a third time: a client that only sends is told nothing.
That is why the leg asserts the other three are NON-EMPTY: identity over empty
recordings would have been a green that could not fail.

This task sends nothing new on any socket, by construction — no `setOutput`,
no `broadcast` call was added — and the measurement is the proof rather than
the claim.

## (j) What F69 must know

1. `currentOrigin.channel == ScriptChannel::TCP` and
   `currentOrigin.connection` are live at the diagnostic funnel — that is the
   routing key, and it is the connection id, so a subscriber table keyed on the
   slot must still check the id (I5, `deliver`'s own pattern at io.cpp:701-710).
2. `originTag()` is the one place the tag's policy lives; the routed feedback
   text should be composed from `where()` + the §11.169 content, not
   re-derived.
3. The leg-(iv) wires are committed as the PRE-F69 baseline: the same battery
   re-run after F69 must reproduce the subscriber's 71 bytes and the plain
   client's 5 bytes exactly, and the feedback subscriber's own wire is the
   positive discrimination.
4. The HTTP door shares the input queue: any "reply to the origin" logic must
   not assume a TCP-origin connection is still open — and an HTTP-origin
   command carries no origin at all, so it routes nowhere by construction.
5. `App::masterput()` is a file-drop poller, not the TCP channel (e).
