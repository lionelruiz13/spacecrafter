# INTENT §11.63

63. **B17 — view_offset / zoom_offset: CHARACTERISED + SUSPENDED. The row's premise (a projection-space offset applied "at the projection stage") is FALSE at source — old applies view_offset in the NAVIGATOR/VIEW stage as a fov-coupled ROTATION, NEVER in the projector; the new pipeline has NO projection-stage offset hook; and old's mechanism IS the "camera rotation" the row forbids. Projection-space-vs-parity is a Vixy decision (2026-07-22, Claude Opus 4.8, dispatch-2026-07-21-opus §1 task 11). NO product code changed.**
    - **(a) THE TWO "CHANNELS" ARE ONE PARAMETER [observed + measured live].** Config `[navigation] view_offset` (SCS_NAVIGATION/SCK_VIEW_OFFSET [define_key.hpp:43/309]) → `Core::setViewOffset` [core.cpp:494-496]; runtime command `set zoom_offset <value>` (ACP_SC_ZOOM_OFFSET="zoom_offset" [base_command_interface.hpp:566]; `m_set[ACP_SC_ZOOM_OFFSET]=APP_ZOOM_OFFSET` [app_command_init.cpp:314]; case → `stcore->setViewOffset(evalDouble())` [app_command_interface.cpp:1781]) → the **SAME** `Core::setViewOffset`. There is NO separate "zoom_offset" behaviour: `view_offset` is the config-channel spelling and `zoom_offset` the command-channel spelling of ONE clamped [-0.5,0.5] scalar (core.cpp:2114-2117), commented "percent of fov radius" (core.cpp:2110), TUI label "Zoom Offset" (ui_tuiconf.cpp:594) — resolving the DoD "distinguish zoom_offset from view_offset": they are the §2(c) two channels of ONE offset, not two offsets. **Measured** [b17_probe.gdb break on Core::setViewOffset, running DEFAULT/new path]: config fired 2 hits at startup (offset=**0.000000**, config value 0); command `set zoom_offset 0.2/0.35/0` fired 3 hits (offset=**0.200000/0.350000/0.000000**); the `=`-form fires **ZERO** args (the 8× spelling trap — `set NAME VALUE` is SPACE-separated: parseCommand reads command then (key value) pairs [app_command_interface.cpp:144-166]); two BOGUS names (`zoom_ofset`, `zoomoffset`) fired **0** hits.
    - **(b) WHERE IT ACTUALLY APPLIES — the NAVIGATOR/VIEW stage, NOT the projector [observed; grep: `view_offset` in navigator.{hpp,cpp}, core.cpp, coreLink.hpp, ui_tuiconf.cpp, define_key.hpp, base_command_interface.hpp, app_command_interface.cpp — NEVER in projector.cpp].** `Core::setViewOffset` [core.cpp:2111] calls ONLY the old navigator: `navigation->setViewOffset(off)` (stores) + `navigation->setLocalVision(InitViewPos)`. TWO application sites, both in Navigator, both scaled by `view_offset_transition`: (1) `setLocalVision` [navigator.cpp:159] `local_vision = yrotation(−view_offset·(π/2)·transition)·_pos` — a scene-space (fixed 90°-scaled, fov-INDEPENDENT) re-aim of the look vector; (2) `updateViewMat` [navigator.cpp:309, per frame] `mat_local_to_eye = xrotation(view_offset·(fov/2)·(π/180)·transition)·mat_local_to_eye` — a fov-COUPLED rotation of the local→eye VIEW matrix. `view_offset_transition` is 0 at rest, driven to 1 only by an auto_move zoom-in / back to 0 by zoom-out [navigator.cpp:73-78] ⇒ **the offset is ARMED by a commanded view move, inert at a fresh un-moved view** (hence "zoom_offset"). Corrects/refines §11.45(d)'s "the yrotation view offset": the PRIMARY per-frame site is the xrotation; the yrotation is a secondary re-aim.
    - **(c) "PROJECTION-SPACE" IS IN EFFECT ONLY, VIA A VIEW-MATRIX ROTATION [derived].** The primary site (updateViewMat xrotation) is ∝ fov/2; on the fisheye transfer (r = θ/halfFov) a rotation of view_offset·(fov/2) shifts the projected center by view_offset·(fov/2)/(fov/2) = **view_offset FRACTION of the dome radius — fov-INDEPENDENT** (the "percent of fov radius"). SCREEN result = a constant fractional dome shift (projection-space-in-effect), but the MECHANISM re-aims the optical axis (the look direction moves by view_offset·(fov/2)) and the visible cone ROTATES in world. A fixed-angle re-derivation would give a fov-DEPENDENT shift (the actual scene-space trap). Old is thus neither pure scene-space nor pure projection-space: it is a fov-coupled VIEW rotation + a secondary scene-space yrotation of the look vector.
    - **(d) THE NEW PIPELINE HAS NO PROJECTION-STAGE OFFSET HOOK [observed].** The new-path projection is GPU fisheye (custom_project.glsl `fisheyeProjectCustom` + fisheye.glsl `fisheyeProject`), replicated across ~8 shader functions, driven ONLY by `ModelViewMatrix` + `clipping_fov = (zNear, zFar, halfFov)` — no NDC-offset input in any of them. The only CPU projection authority (ProjectionTransfer.hpp) computes radial transfer for screenPos consumers (halo/hint/pointer/label anchors), NOT the render matrices. Camera [Camera.hpp] exposes `viewRotation() = Z(heading+π)·X(π/2−alt)·Z(az−π/2)·F` + `placementRotation` — NO offset member; `Renderer::getClippingFov()` returns a Vec3f (no room for an offset). A TRUE projection-space view_offset (image slides on the dome, optical axis UNCHANGED — the DoD discriminator) **cannot be expressed in the Camera matrices** (any matrix-level offset IS a rotation ⇒ changes the look direction); it would need an NDC-offset uniform added to the SHARED GPU projection shaders — which ALSO touch the OLD path and would DIVERGE from old at the dome edge (a pure NDC shift leaves a blank crescent + clips where old's fov-coupled rotation FILLS the disc with a re-aimed cone). The Vulkan-viewport-offset alternative is rejected: it is a GLOBAL state that shifts UI/overlays too (old shifts only the scene view matrix, not the ortho2D UI).
    - **(e) THE CONFLICT (reported, not resolved) → SUSPENDED FOR VIXY.** **Source A** (old-path implementation = the parity spec): view_offset is a fov-coupled VIEW-matrix ROTATION [navigator.cpp:159,309] — it DOES change the optical-axis world direction; the visible cone ROTATES; armed by a commanded move; and the tester's tilted-dome shows use THIS today. **Source B** (this row's spec / §13.B B17 / the DoD): view_offset is PROJECTION-SPACE, "must NOT re-derive as a camera rotation", optical axis must stay FIXED. On flat FISHEYE they give the same center displacement but differ at the dome edge and in the look-direction observable (Camera forward moves under A, fixed under B). **Irreconcilable without a Vixy decision** — implementing A defies the DoD; implementing B is a new architectural shader hook that touches the old path and diverges from old at the edge (user-visible-semantics beyond old's surface). Per the row's own "Where to stop" (*"if the new path lacks the projection-center hook … suspend rather than approximate it as a rotation"*) and the I-rules (an improvised architectural / user-visible-semantics decision = failure): **SUSPENDED** (question + 3 options in §13.B B17).
