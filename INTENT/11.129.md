    - **(b) WHAT THE §5.63 ATTEMPT EXCLUDED — and one thing it CORRECTED about the row itself.**

The two lit sets are **positionally disjoint**, median nearest-neighbour distance **50.2 px ≈ 1.1°** at fov 45 on a 2048 dome. A mean-and-bbox statistic cannot see this; a set comparison can. **The lesson is the general one**: a difference summarised by an average has not been looked at.

      * **Rotation of the old view frame EXCLUDED**: best-fit rotation about the dome centre over ±180° (2° then 0.25° steps) reaches overlap 0.007, and **the milky way is in the SAME place in both** while the star/DSO field is not.

    - **(c) THE READ HALF, and why it was one problem and not ninety-seven.** `AppCommandInterface::readFlag(FLAG_NAMES, bool&)` answers *"what is this flag now?"* for all 97 flags in one place, and `setFlag`'s FV_TOGGLE branch is now its **consumer**: the toggle reads the authority, negates, and falls into the same write the `on`/`off` path uses. Before, the only code that knew a flag's value was that switch, and it knew it **only while mutating it** — which is precisely why §2's row E3 had no save half (§11.128(e)) and why §11.108's census recorded E4's readback as *"NOT established"*. The same extraction gives `readValue` (**30 of the 43 `set` names**; the other 13 write into sinks nothing in the tree can read, and `set mode` writes nothing at all) and `readColor` (**44 of 46**), plus `applyColor` extracted out of `commandColor` so a restore drives the same write the command does rather than a second copy of it.
      **Three façade read halves were missing where the manager already had the getter** and are added: `CoreLink::skyDisplayMgrGetColor` (nine colour names had no readback for want of one forwarder), `CoreLink::constellationGetColor`, `CoreLink::atmosphereGetFadeDuration`. `App::asBool(APP_FLAG)` and `Ui::asBool(UI_FLAG)` are the same shape one layer out.
      **TWO DEFECTS FELL OUT OF THE EXTRACTION and are fixed with it** — both invisible while nobody could ask a flag its value:
      * **26 flags — every sky grid and every sky line — reported the value the flag had BEFORE the toggle.** Their branch read the getter *without negating it* and then called `Flip`, so `newval` (which feeds the recorded command line, `flag <name> <value>`, and the status readout) carried the pre-toggle value.
      * **6 more never wrote `newval` on a toggle at all** (the App/Ui-owned ones), so `AppCommandInterface::setFlag(FLAG_NAMES, FLAG_VALUES)`'s `bool val;` stayed **uninitialised** and was read.
      **A third was caught by the gate rather than by reading**: `flag satellites` READ the stored *hide-satellites* bit as if it were the command's *show-satellites* flag (`ProtoSystem::toggleHideSatellites` inverts its argument before storing it, `protosystem.cpp:261`), so `flag satellites toggle` was a **no-op in one direction** and a save recorded the opposite of what it would restore. Found because the T4 fixed point failed by exactly one line (11816 vs 11817 B, `satellites = false` → `true`); fixed by reading `!hideSatellitesFlag()`; T4 byte-identical afterwards. **The round trip is a better instrument for polarity than the eye is.**
      **WHAT IS PRESERVED RATHER THAN SIMPLIFIED**: `flag star_names` drives three underlying states (stars, star-navigator, Tully) and `flag nebula_names` two, each toggled from its OWN value. `readFlag` reports the PRIMARY and those cases keep their per-sub-flag toggles, because those are different state, not a second copy of one state. Collapsing them would have been a silent specialization; it is named here instead.

    - **(e) THE LEDGER, AND WHY IT IS A DELTA (D30).** One `[body:<englishName>]` section per body carrying an override, keyed by the plain name **D34** chose. Every body now keeps **what the DATA gave it** — halo colour, raw nav radii, the declared hidden bit, and each module's own authored colour — and a field reaches the file only when it **differs**. Consequences, each measured:
      * a body nobody touched has **no section at all** (Saturn absent from an 8-entry ledger);
      * the **system-qualified tree path** is written in every entry **for the miss report and for nothing else** (D34: the key is the plain name, the path is context);
      * the baseline is taken **where nothing else can have written yet** — a module's colour in the module's constructor, a body's at the END of `loadBody` (after `hidden = true` is applied by calling `hide()`), and again at an engine-minted body's own creation site (`CameraAnchors.cpp`: an anchor's body is hidden **by construction**, and the first version read that as somebody's override — 8 spurious entries, caught by looking at the file).
      **Rows carried**: D1 hidden · D2 scale (the COMMANDED target, kept on the body because `ASmooth` folds its target into coefficients the moment a ramp starts — D32's settled value) · D3/D4 the four colour channels · D6 datum/ground radius · D7's scalar half `skin_use` (the created skin is a texture path and stays with content, per its own row) · D8 the per-body orbit/trail override, and **only when it is live** (a global toggle stales it, which `wantShown` already treats as "follows the master") · D10 the accumulated trail points, written whole. **D5** (the runtime colour DEFAULTS) is its own `[body_defaults]` section and a snapshot rather than a delta, because no body authored them and they are invisible in any per-body view — they change what FUTURE bodies get. **D9** is `[tesselation]`, global by construction (one shared object, nothing per-body). **D11 EXCLUDED** (old path).
      **D10's SHAPE, decided from D32's verbatim** rather than assumed: trail points are one of D32's three named carve-outs from *"transients snap to their settled target"* — *"persistent conditions and drawn content, not motions"* (§11.113(k)). A trail is drawn content that took simulated time to accumulate, so it is written whole rather than re-derived: re-derivation exists (`resumeAfterHidden`) but needs an orbit, and a body without one would come back empty with nothing to explain it.
