## (a) THE GAP, MEASURED: an entire play, and not one byte on the wire

A client connected on 7805 and subscribed with `$LOGON` played a four-line script
that contains one block fault. The engine ran it, wrote its diagnosis into the file
(`#!` tail on the faulty line, §11.184's channel), and reached its natural end.

**After the subscription's own confirmation, the connection received ZERO bytes for
the whole play** `[measured: f67_tcp_live.py leg D, `engine lines after the
subscription: 0`, artifacts/f67/f67_result.json]`. No acknowledgement that the play
started; no event when it ended; not one of the diagnostics it produced.

That is not a property of this script. Only **two** things ever reach a client:

1. the answer to `get status …` and to `search name …`
   `[observed: app_command_interface.cpp:1284-1301, :1415 — the ONLY callers of
   `ServerSocket::setOutput` in the whole tree, verified by grep at `116f6d19`]`;
2. the inline replies to `$NOTICE` / `$LOGON` / `$LOGOFF`
   `[observed: io.cpp:640-663]`.

Everything else the engine has to say about a command goes to `debug_message` and
from there to the script log at `L_DEBUG` — §5.117's chokepoint. Including the one
message an operator would most want: `"Unable to execute script : <path>"` for a
play that could not open its file `[observed: app_command_interface.cpp:2889]`,
which F61 read out of the LOG for exactly this reason.

**Confirmed by the positive control in the same run**: a `get status position` on the
same connection is answered in the same second (leg B). The channel works; there is
simply nothing addressed to it about a script.

**[RE-MEASURED 2026-08-31 → §11.187(g), F68, on a THIRD independent instrument: still exactly two.** A `$LOGON` subscriber, two plain clients and an HTTP request recorded every byte they received across a battery of five refused commands and a played script, on the pre-change binary twice and on the delivered one: 71 B to the subscriber (its own confirmation, one broadcast answer, one HTTP notice), 5 B to the client that asked a `get`, **0 B to the client that only sent** — byte-identical in all three runs `[measured: harness/artifacts/f68/wire.*.bin]`. That 0 is this gap, measured a third time and now committed as F69's frozen-wire baseline. Citation drift, same date: the *"Unable to execute script"* line is `app_command_interface.cpp:2914` at `423cbe23` (`:2889` was correct at `5d3d577f`), and the `setOutput` callers are `:1309-1326` and `:1440`.]**

## (b) The consequence, stated as a client sees it

A TCP client cannot distinguish, from the wire alone:

| | |
|---|---|
| a command that ran | a command that was refused |
| a script that is still playing | a script that ended a minute ago |
| a script that ended normally | a script that could not be opened at all |

`flag stars on` and `flag stars onn` are the same silence. The only way to learn
anything is to ask a question the engine does answer (`get status …`) and infer, or
to read the engine's log file — which requires being on the same machine and
knowing where its `$HOME` is.

This composes with two rows already open and is not covered by either. **§5.72**
records that the `$LOGON` channel's greeting promises the logs and it delivers other
clients' command ANSWERS; this adds that it delivers no log line and no lifecycle
event either — the greeting is wrong in both directions. **§5.117** records that the
157 refusals are written at the wrong severity; this adds that they are written to
the wrong *place* for any client that is not local. Both rows carry a back-marker to
this entry.

## (c) The workaround scedit took, bounded and disclosed

Because there is no end-of-script event to wait for, scedit's editor watches the
FILE: after a play, and only then, it re-reads the played file **at most once a
second, for at most five minutes, until it changes** — I3's admitted case (an
external writer with no notification channel), with both numbers in `sc_tui.hpp` and
in `util/scedit/README.md § Live mode`. It is a convenience and not the guarantee:
the guarantee is that `EditCore::save` compares the file with what it read **before
every save, always**, play or no play, and refuses rather than choose which of the
two authors loses (measured both ways, §11.185's sibling record in the scedit mirror
ledger journal `2026-08-31h`).

A workaround is the right word. A single line on the feed at `terminateScript` —
"script `<path>` ended, N diagnostics" — would replace the whole poll with an event,
and the poll would still be needed for any OTHER writer of the file.

Three things, none decided here:

1. **Should the control channel carry script lifecycle at all?** The reading in which
   this is not a defect is real: the log is the engine's error channel by design, and
   a control protocol that says nothing is a protocol whose clients cannot come to
   depend on what it says. The reading in which it is one: `io:enable_tcp` is shipped
   **true**, `capability-surface.md` §1 row 2 calls it the LIVE control channel, and
   §2(f) asks that a refusal be actionable — which it cannot be to the only party in
   a position to act.
2. **Does this warrant its own §5 row, or is it §5.72 + §5.117 read together?**
   BOTH READINGS RECORDED, neither enacted. *Own row*: it is a distinct
   reachable-with-consequence fact from a shipped surface (§5.79's criterion) that
   neither existing row states — §5.72 is about what the feed carries, §5.117 about
   severity, and "no lifecycle event exists" is neither. *No new row*: a third row
   over the same channel with the same owner and the same fix would be one more
   thing to keep in step (I2), and the two rows now carry the measurement by
   back-marker. The executor took the cheaper, reversible option — annotate, do not
   mint — and says so here; minting §5.119 later costs one edit. **[NUMBER
   CONSUMED 2026-08-31, F71: §5.119 now names an unrelated row (the

3. **Who may move the dome?** Scedit's MCP `run_command` reaches whatever listens on

   `util/scedit/README.md § For machines` so that binding the tool to a machine which
   can reach a real dome is a decision somebody takes rather than a default.

## (e) F27's fix, confirmed live by a client that is not the harness

Two of §11.135's claims were re-measured by an independent implementation
(scedit's `sc_tcpclient`, written from `io.cpp` rather than from `f27_reply.py`):

- **§5.47's addressed copy holds**: `get status position` is answered on the socket
  that asked `[measured: leg B]`, and **exactly once** although the same client is
  also a `$LOGON` subscriber — `deliver`'s exclusion of the addressee is live and
  correct, not merely written.
- **§5.72's broadcast holds**: a SECOND, unsubscribed client's answer arrives on the
  first client's feed `[measured: leg C]`. The conflation §11.135(c) left as a veto
  point is still exactly what it was, now with a third witness.

Adjacent, recorded not chased: the `$LOGON` confirmation
(`"Vous receverez maintenant les logs"`) is itself an engine record on the wire, so
any count of "replies to my commands" that does not exclude it is off by one — which
is how F67's own instrument went red twice on its first run before the count was made
about the commands.

## (f) Host state during the measurement, disclosed (§11.174(h))

The `claude` session's screen was LOCKED at the first run (`GetActive` true), which
throttles the engine to a 1 Hz frame clock (`HOST-EVENTS.md` 2026-08-31). The
instrument READ that, RECORDED it, then woke the session
(`org.gnome.ScreenSaver.SetActive false` + `SimulateUserActivity` each minute) and
recorded that too. **That is a mitigation, not a fix, and it is an owner veto item.**
Frame stalls: **1 and 2 per run** here, against **105/run** measured on a locked
session (§11.183) — the runs were on an awake compositor. None of F67's claims is a
timing claim; the wake matters only because a 1 Hz engine makes a five-minute window
mean something different from what it says.
