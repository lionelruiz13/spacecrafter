## (e) THE DISCRIMINATION

Against the reference values, classified — not compared:

1. **The §5.52-carrying child, rebuilt at `2117ccb0` and measured two days later, reads the
   FIRST-epoch numbers.** Jupiter **3888 / 3884** where the shifted epoch read **5045**;
   the Sun's 19666 is bit-identical to both recorded epochs; Mars 6814 / 6775 sits in the
   6738–6814 band of the unshifted runs and nowhere near 7067. The excess the row is about
   (+1157 counts on Jupiter, +29.8 %) is **≈ 290× the child's own in-epoch A/A spread**
   (4 counts), and Mars's +272 (+4.0 %) is ≈ 7× its spread (39) — so its absence today is
   not a floor artefact.
2. **The pre-§5.52 binary reads its own recorded signature bit-identically, twice**
   (0 / 0 / 444 new; 23536 / 7683 / 3908 old; ratios 0.0000 / 0.0000 / 0.1136). Everything
   this scene can see that does not require the fix — both paths' geometry, the fov search,
   the old-path discs, and the 444 counts of non-disc new-path content inside Jupiter's
   disc mask — is unchanged across two days.

**⇒ The shift is not carried by the delivered code**: the identical source, rebuilt from a
clean worktree, does not reproduce it. **⇒ It is not carried by any persistent host or
app state this scene can see either**: nothing the pre binary can show has moved, and the
child's own numbers came back to the first epoch's. **⇒ It was a transient of the epoch-B
session** (00:02–00:07 on 2026-08-01), reproducible twice *within* that epoch and not
outside it. §5.62 therefore does **NOT** escalate: record-don't-chase stands, and the
delivered code is exonerated at the row's own bar.

**⇒ The row's consequence stands unchanged and is now stronger, not weaker**: a quantity
that reads 3888 in one epoch, 5045 in the next and 3888/3884 in a third, against an A/A
floor of 4 counts, is not comparable across epochs. In-epoch pairs only.

### The owed measurement could not, on its own, have discriminated — and that is recorded

The task's dichotomy had two branches: *pre shows the shifted values too* ⇒ accumulated
state; *pre shows first-epoch values while the child shows shifted ones* ⇒ code implicated.
**The first branch is void by construction**: the pre-§5.52 binary draws **no mid-band disc
at all** — that is precisely what §5.52 is — so on the Sun and Mars it has no observable
that could carry a shift, and on Jupiter it can only carry the 444-count non-disc content.
The second branch did not fire either, because the child did not show the shifted values.
**The leg that actually discriminates is the child in a NEW epoch**, and the pre binary's
value is as the epoch anchor: it is what says the environment did not move. Both legs were
taken, so the row is answered; but the row's own statement of what it owed was one binary
short, and that is corrected here rather than glossed.

§5.62 records, as ruled out en route: *"`active.lock` is a crash-log ROTATION marker only …
it explains the 45-byte `app.log` and the missing Vulkan-loader debug lines in the late
runs, and therefore retracts any validation-layer-absent reading of those runs"*.

**Measured against it:** F26's `child_1` launched **with a stale `active.lock` present**

between]`, the rotation branch **positively fired** `[observed:
~/.spacecrafter/log/EntityCore-logs-1785679232033264565.txt — suffix = the rename time in
ns, 1785679232 s = 2026-08-02 15:59:5x; the log directory's own mtime is 16:00]`, and that
run produced a **229 966-byte `app.log` carrying the loader debug lines and the layer's
load line**. Mechanism agrees with the measurement: the branch at
`VulkanMgr.cpp:225-233` renames three files under `log/` and creates the marker otherwise —
it cannot touch the shell redirect the driver captures stdout with, and no `dup2` of stdout
exists anywhere in `src` `[observed: grep stdout-logs/preserveCrashLogs — two sites, both
in VulkanMgr]`.

So the 45-byte capture of the two shifted runs is **unexplained**. What it contains is
exactly one line — `terminate called without an active exception` `[observed:
artifacts/f18_final/app.log, f18_final2/app.log]` — with no loader output at all, while
every unshifted run (three in epoch A, four in epoch C) carries ~230 KB and exits cleanly.
Two consequences, both recorded rather than chased: (1) **the epoch-B runs' instrument
state is not positively recorded** — the retraction of the "validation layer absent"
reading rested on the refuted explanation, so what those runs had loaded is simply unknown
(the most economical reading is that they were launched by a different command than
`f18_run.sh`, whose `VK_LOADER_DEBUG=layer` is set inline; nothing in the artifacts decides
it); (2) **the launch/exit path is the only other observable that separates the two shifted
runs from the six unshifted ones**, which is where a future attempt at attribution starts.

The two shifted runs also agree with each other **to the digit** (7067 / 5045 twice) while
the unshifted runs of both epoch A and epoch C do not (Mars 6738 / 6781 / 6775 / 6814) —
the shifted state was *more* deterministic than the normal one, which constrains any
mechanism proposed for it.

What is **available but deliberately not taken**, so the next attempt does not have to

the class this row exists to forbid for live numbers — and it is diagnosis, not the owed

Two candidate directions the data admits, both **[assumed — flagged]**, neither tested:
the three bodies split exactly along texture use (Sun procedural and bit-stable, Mars and

than at geometry; and the shifted runs' unclean exit points at a disturbed device/driver
state carried across launches within that session. Attribution needs the transient captured
live, and nothing today can produce it on demand — which is why the row stays open.

## (h) Deviations, each with its argument

1. **`-j8`, not `-j6` or `-j$(nproc)`.** `free -g` measured **38 GiB available** before
   each build ⇒ the standing rule (< 16 GiB ⇒ `-j6`) permits `-j12`; `-j8` was used to
   leave headroom for the concurrent sessions that caused the 2026-07-30 host OOM.
2. **Worktrees rather than sequential checkouts in the main tree.** The main tree never
   left `master-beta @ d9de42ac` and was clean at every point; an abort could not have left
   a detached HEAD behind. Both worktrees were clean at their named commits before the
   builds `[observed: git -C <wt> status --porcelain = empty]`.
3. **The concurrency probe was replaced** (§(b)) — a required precondition whose stock
   instrument both under- and over-reports for this campaign. The replacement is positively
   mapped both ways.
4. **`run.log` was destroyed in all four runs** by `f18_run.sh`'s own first act
   (`rm -f "$OUT"/*.log`), which unlinks the file the wrapper's redirect is writing to.
   Nothing load-bearing was lost — the binary, the concurrency count, the md5s, the layer
   state and the driver's own output are in `f26_meta.txt`, `app.log` and `drive.log`, all
   written after the clear — and the wrapper now writes `run_stdout.txt`, which the clear
   does not match. The campaign was not re-run for it: the lost file duplicated evidence
   that exists elsewhere, and a re-run would have cost the epoch its interleaving.
5. **The task's discrimination dichotomy is answered by a third branch** (§(e)), stated
   explicitly rather than forced into one of the two.
