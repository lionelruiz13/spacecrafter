# INTENT §11.34

34. **Orientation-convention divergence (P5) — ROOT CAUSE DERIVED (2026-07-17; Vixy mandate: "user scripts can't be modified, so the missing orientation class shall be managed in the least intrusive way in the new path"; question asked: "what is exactly the root cause structurally, and why it existed in the first place"). ANALYSIS ONLY — nothing implemented, nothing committed; implementation is a next-session item.**
    - **The root, in one sentence**: the old path's `rot_local_to_parent` carries TWO roles under one name — (a) the body's own axial tilt for rendering, and (b) the frame conversion from the body's equatorial frame into its PARENT's frame — and the shipped rotation data is authored under role (b)'s **nested-frame convention** (a satellite's `rot_obliquity` is stated *relative to its primary's equator*, not to the ecliptic). §5.11's flat-chain fix removed the per-hop parent rotation — correct for POSITIONS (ephemerides are root-aligned) — but the rotation data was never re-expressed, so the new path now feeds nested-convention numbers to a flat consumer.
    - **The two composition sites** [observed]: OLD `Body::compute_trans_matrix` (body.cpp:534-546) computes `rot_local_to_parent = zrotation(node − prec·(jd−epoch)) · xrotation(obliquity)` **inside `if (parent)`** — a parentless body keeps the ctor's `Mat4d::identity()` (body.cpp:129), with the stated reason on the guard: *"Special case - heliocentric coordinates are on ecliptic, not solar equator..."*. OLD `Body::computeDraw` (body.cpp:1000-1017) then right-multiplies **one** ancestor level into the drawn matrix: `mat = T(p_ecl) · mat · p->rot_local_to_parent[_unprecessed]`, i.e. rotation part = `R(self) · R(parent)`. NEW `ModularBody::computeBodyPosToBody` (ModularBody.hpp:379-384) computes the same tilt **unconditionally and with no parent term** — flat chain by contract (ModularBody.hpp:335-347).
    - **Why it existed — derived, three layers**:
      (i) The design was a **full ancestor chain**: `getRotEquatorialToVsop87` (body.cpp:552-559) still walks every ancestor (`for (Body *p = parent; p; p = p->parent) rval = p->rot_local_to_parent * rval`). Under a nested-frame convention that walk is correct and the data is coherent (see the Charon proof below).
      (ii) The draw-side walk was **truncated from a loop to one hop** — the in-source comment is the direct evidence: `if (p) {   //this loop worked to enable moons when while but now with if ?` (body.cpp:1000), under a `\todo account for moon orbit precession (independent of parent) / also does not allow for multiple levels of precession`. Someone hit the moons case, found the chain walk wrong (because the ephemerides are root-aligned, so nesting the TRANSLATIONS is wrong — the E2 class §5.11 fixed), and **reduced the walk instead of tracing the root**: the translations went flat (right) and the rotation half stayed (as a one-level right-multiply). That is the patch, and it is the origin of the whole class. Zero-patch, exactly: the adjacent failure space (the rotation half) was left intact and kept accumulating.
      (iii) The truncation also put the parent rotation on the **wrong side** — draw does `R(self)·R(parent)`, the accumulated frame is `R(parent)·R(self)`. Invisible in shipped data because every non-identity case has both ascending nodes == 0 → pure x-rotations → they commute. A third accidental-correctness layer.
    - **The data proves the convention** [observed: ~/.spacecrafter/ssystem.ini]: Moon `rot_obliquity = 23.45`, `rot_equator_ascending_node = 0`; Earth `rot_obliquity = −23.4392803055555555556`, node absent (0). Old's Moon net = `x(23.45)·x(−23.43928) = x(0.0107°)` — the declared 23.45° is **the negation of Earth's obliquity to within 0.011°**, i.e. a pure compensation constant for the stray parent term, carrying no physical meaning (the Moon's true obliquity to the ecliptic is 1.54°). **The decisive case is Charon**: `rot_obliquity = 1.0` with parent Pluto at `−115.60` → old net `x(−114.60°)`. Charon is tidally locked in Pluto's equatorial plane, and Pluto's true obliquity is ~119.6° — so `1.0` is ONLY meaningful as "1° from Pluto's equator". The nested convention is not an inference from one body; it is what makes the shipped data physically correct.
    - **The divergence set is CLOSED and small — 7 bodies** [derived from the full ssystem.ini rotation table, then checked exhaustively]: the stray factor is `R(parent)`, so it is identity wherever the PARENT has no declared obliquity. Only three parents have one: **Sun (7.25)** — but old's `if (parent)` guard makes its rotation identity, so *every planet already matches* (this is why Earth-reference scenes measured green, §11.26/§11.27); **Earth (−23.4393)** → child **Moon**, error **23.4393°**; **Pluto (−115.60)** → children **Charon, Nix, Hydra_, Styx, Kerberos**, error **115.60°** each. Plus **the Sun itself**: old suppresses its declared 7.25°/196.13° via the parentless guard, new honours them → error 7.25°. Every other moon (Mars/Jupiter/Saturn/Uranus/Neptune/Haumea systems) has a parent with obliquity 0 → **no divergence**. The Jupiter/Uranus/Neptune `15.5°/213.7°` cluster is a copy-paste default, inert for the same reason.
    - **Answer to the mandate's question — can it be fixed by declaration only? NO for the moon class, YES-but-undesirable for the Sun.** [observed: app_command_interface.cpp:3554-3560 `body action load` → `Core::addSolarSystemBody` → "a hash of parameters **mirroring the ssystem.ini file**"] — **user scripts declare bodies with the very same `rot_obliquity` key**, under old's nested convention. So editing ssystem.ini cannot cover script-declared satellites, and Vixy's constraint (scripts immutable) rules the data-only route out **by construction, not by cost**. The Sun could be silenced with `rot_obliquity = 0` on `[sun]`, but that deletes a physically-correct value to reproduce a defect, and a script could still `body action load` a parentless body.
    - **THE FIX — "one concept, two consumers" CONFIRMED structurally by design (2026-07-17, verified against the counter-hypothesis, not assumed)**. The concept is **the body's equatorial (lat/lon) frame**. Its two consumers:
      * **Camera/observer declaration frame** — `dispatchUpdate` [observed: ModularBody.cpp:168] `flat = mat_local_to_body · body->accumulatedBodyToBodyPos(jd)`, under its own comment: *"The camera mat is the reference's ACCUMULATED equatorial frame (its surface/spin composition and the body's lat/lon grid are defined there ... leave the accumulated frame exactly once, here"*. Uses the **accumulated** frame.
      * **Mesh render frame** — `recursiveUpdate` [observed: ModularBody.cpp:150] `mat = matLocalToBodyPos · computeBodyPosToBody(jd)`. Uses the body's **own tilt only**.
      **These two MUST be the same frame** — not as a preference: the body's texture is lat/lon-mapped and the observer stands ON that mesh, so an observer at (lat,lon) must be above the mesh point at (lat,lon). The header states the premise itself [observed: ModularBody.hpp:397-399]: *"A body's lat/lon grid is defined in the frame accumulating the parent rotations"* — **and the render path contradicts it**. Algebra: with the camera declared in `A = accumulated`, `flat = C·A⁻¹`, so today `mat = C·A⁻¹·R(self)` ≠ `C`; routing the render through `A` gives `mat = C·A⁻¹·A = C` **exactly**. Verified numerically (2026-07-17): new observer vs new render on the Moon = **23.4421°** (the wiring gap); fix vs new observer = **0.0000°**. So the new path currently runs **two contradictory frame conventions at once** — the observer path implements the nested convention the data is authored in, the render path implements a flat convention the data does not follow. This is an **internal contradiction, independent of the old path** — a strictly stronger confirmation than parity, and it is the reason the fix is the right one rather than merely a matching one.
      **It generalizes implicitly** (all four for free, each a case old gets wrong): (i) **depth** — `accumulatedBodyPosToBody` walks EVERY ancestor; old truncates at one hop (its own `\todo also does not allow for multiple levels of precession`), so a moon-of-a-moon is correct here and wrong there; (ii) **order** — the accumulated product `R(gp)·R(p)·R(self)` is the correct nesting; old's `R(self)·R(p)` is the wrong order and survives only because every non-identity case has both nodes == 0 (pure x-rotations commute); (iii) **the Sun** — the `isSystemCentered()` guard is already inside the walk; (iv) **scripts** — structural, so `body action load` bodies are covered with no data migration. One site, I2 (one authority for the equatorial frame).
    - **Correction to this entry's first draft (2026-07-17, same session)**: I wrote that old "gates the parent-rotation variant on an ORBIT property — a role conflation". That was **wrong on the mechanism**. Verified: `useParentPrecession`'s *declared* meaning — *"Do the body coordinates precess with the parent?"* [orbit.hpp:65] — **has no implementation at all**. `EllipticalOrbit` stores `m_UseParentPrecession` in the ctor and never reads it (`rotate_to_vsop87` is built from the `parent_rot_*` constants regardless, orbit.cpp:405-437); its **only behavioral reader in the whole tree** is the ORIENTATION composition at body.cpp:1003 (plus a debug dump at body.cpp:1359). So it is not a conflation of two live roles — it is a flag whose documented role is **dead**, and whose sole real role is selecting a parent-rotation variant for the rendered orientation. Same class as `ring_shadow` (A3.7): a key that reads as data-model but is a rendering switch.
    - **Precondition/premise of the decision — PRECESSION, and old is not self-consistent here** [derived + verified numerically 2026-07-17]: old's two consumers **disagree with each other**. Old's observer = `getRotEquatorialToVsop87` = **precessed** ancestor product [body.cpp:552-559]; old's render (Moon) = **unprecessed** Earth [body.cpp:1003, `lunar_special` sets the flag false, orbit.cpp:806-809]. Measured: **old_observer vs old_render = 0.3631° at 2026** (a longitude shift; `precessionRate` is rad/day in BOTH paths — `*M_PI/(180*36525)`, verified protosystem.cpp:929 vs ModularSystem.cpp:455 — so Earth's 1.39639 °/century over 26 y = 0.363°, growing ~0.014°/yr). **Therefore no single choice reproduces old at both consumers — old has no self-consistent answer to reproduce.** The fork:
      * **(A) accumulated + precessed at both consumers** — self-consistent by construction; **matches OLD'S OWN OBSERVER exactly (0.0000°)**; residual vs old's *render* = 0.3631° (2026), i.e. exactly Earth's precession, and old's render is the side that disagrees with old's own observer.
      * **(B) mirror old's render bit-for-bit** — reproduces the pixels, but **preserves old's 0.363° observer/render contradiction inside the new path** and re-splits the concept into two consumers again, undoing the fix's entire premise.
      **Recommendation: (A)**, on a derived argument rather than taste — the data is under-determined on this question (the Moon's obliquity is a compensation constant, so its J2000-vs-true-of-date epoch was never authored), and the residual being chased (0.363°) sits inside a model whose own obliquity error against physical truth is **1.529°** (declared net 0.0107° vs the Moon's true 1.54° to the ecliptic) — **4× larger than the term it would preserve**. Optimizing the 0.363° while the 1.529° stands is fitting noise. (B) is available if a measured A/B says the 0.363° is visible and unacceptable at the row-2 terrain scale — decide on evidence, not on this note.
    - **Second precondition — fold-at-load vs per-frame**: in shipped data every non-identity factor is time-invariant (Moon → unprecessed → constant; Pluto → no precession → constant), so a load-time fold into the child's `re` would work and cost nothing per frame. It is **NOT general**: a script-added satellite of a precessing parent with the default `useParentPrecession = true` has a time-varying factor. Under (A) this precondition **dissolves** — the accumulated walk is already per-frame and already correct, and no fold is needed. It only returns if (B) is chosen. Decide on the general case, not on the shipped one (anticipate the class, not the instance).
