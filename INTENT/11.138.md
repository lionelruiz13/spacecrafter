number to the digit.

**Run `lvp1`** `[measured: harness/artifacts/f30/lvp1/gdb.log]`: **434** allocations

**It is ONE BUFFER, not a pool, and not one the memory manager sizes.** Three independent
facts say so `[observed: src/EntityCore/Core/MemoryManager.cpp, src/main.cpp @ bd3f7117]`:

1. The pool's `chunkSize` is **256 MiB** — `main.cpp:319` passes `.chunkSize=256`, and

   it. (`VulkanMgrCreateInfo::allowOverrides` is set true at `main.cpp:322` but is **read
   nowhere in `src/`** — 2 occurrences in the whole tree, the declaration and that
   assignment — so no override reaches `chunkSize`.)
2. `registerChunk=false` in the frame. `allocateChunk`'s registering default is `true`;
   `false` is passed only where the size is a RESOURCE's own `memRequirements.size`
   (`:140`, the over-a-chunk branch, and `:157`, the host-visible branch). The allocation
   is consequently NOT pushed onto `memoryChunks`, its `SubMemory::size` is set to
   `(VkDeviceSize)-1`, and `MemoryManager::free` releases it with a direct `vkFreeMemory`
   (`:75-76`) instead of returning it to a free list. It is a whole allocation owned by
   one resource, by construction.
3. The size is exact arithmetic from the video player's own two constants, with no
   rounding anywhere: `computeTextureResolutionLimit()` returns `32*MIBI+MAX_CACHED_FRAMES`
   for a host with ≥ 15 GiB of RAM `[observed: video_player.cpp:38-45]`, `MAX_CACHED_FRAMES`
   is **80** `[observed: video_player.hpp:52]`, `MIBI` is `1024*1024`
   `[observed: call_system.hpp:34]`; this host reports 59 GiB `[measured: free -g]`, so
   **(33 554 432 + 80) × 80 = 2 684 360 960** — the row's number to the byte. (The
   6 400 B by which it exceeds 2 560 MiB is `MAX_CACHED_FRAMES` × `MAX_CACHED_FRAMES`: the
   helper adds a FRAME COUNT to a per-frame BYTE size, then the caller multiplies by the
   frame count again. Recorded, not judged.)

**Run `native1`, the regime control** `[measured: harness/artifacts/f30/native1/gdb.log]`:
the same buffer, the same name, the same `bufferBlocSize=2684360960`, the same callsite
chain — on the proprietary driver, with **0** `maxMemoryAllocationSize` warnings. The only
difference is the route inside the manager: `memDedicated.prefersDedicatedAllocation` is
true there, so it goes through `dmalloc` (`MemoryManager.cpp:58`) rather than
`allocateChunk`. Both routes are one resource. So **the request is unconditional and
ICD-independent — it is computed from HOST RAM and a compile-time frame count — and only
the enforcement differs.** (Three allocations above 1 GiB on native, two on llvmpipe; the
runner-up on both is 1 610 612 736 = `3*512 MiB`, the `"Texture staging BufferMgr"` of
`app.cpp:480`, at 75 % of the limit — the next one in line to cross it.)

**Two facts the fix domain turns on, both stated because D13 needs them:**

- `maxMemoryAllocationSize` is queried **nowhere in `src/`** (0 occurrences). There is no
  fallback path to tune; there is no path.
- The failure path that does exist is a bare log. `BufferMgr::BufferMgr` logs
  *"Failed to create buffer bloc"* and RETURNS `[observed: BufferMgr.cpp:8-11]`, leaving
  the manager constructed with no buffer, no `insert()`ed free space and no mapped `data`;
  `VideoPlayer::createTextures` then builds four `Texture`s on it. Nothing throws, nothing
  is signalled to the caller. On a conformant device that enforces the 2 GiB limit the app
  continues with a silently unusable video staging manager.

**So the fix domain is NOT a policy on pool sizing.** It is (i) the video player's own
single-buffer sizing policy — a RAM-tiered per-frame cap times a fixed 80-frame cache,
chosen from host RAM but spent on a device allocation, and taken **unconditionally at
startup** (`App::firstInit`) whether or not any video is ever played — and/or (ii) a
fallback path, which today does not exist at either end. Both are outside `MemoryManager`.

**One correction to the row's implied chain:** on the measured ICD the oversized
allocation **SUCCEEDED** — the validation layer only warns, and the app's own log records
*"Allocate chunk of 2560 MiB in GPU memory."*, which is the success branch. The row already
said the chain from the allocation to the rc=139 was not established; it is now sharper
than that — on llvmpipe the allocation is not what fails. Nothing here explains the SEGV,
and nothing here claims to.

## (f) §5.72 — YES, and the two shipped clients fall on OPPOSITE sides of the decision

Corpus §(g), 1158 files. **`$LOGON` — 8 hits in 4 files** `[measured: corpus_report.txt]`;
control on the same channel, `socket|tcp`, returns 235 hits in 26 files.

- **Producer / advertiser:** `src/tools/io.cpp:644` — the server offers
  `$NOTICE $LOGON $LOGOFF`. (The three remaining `src` hits are §11.135's own comments.)
- **`util/server_standalone/recever_client.c:46`** — `char login[]="$LOGON";`, written to
  the socket, then a `while` loop of `read()` + `printf`. It issues **no commands at all**:
  the feedback stream is its ONLY source of anything.
- **`util/server_standalone/send_recev_client.c:53`** — `char login[]="$LOGON\n"`, then the
  subscription confirmation is read, and then it issues `get status constellation`,
  `get status position` and `search name m1`, **reading the answer off that same socket
  after each one**.

**So the row's question is answered YES:** a shipped client subscribes with `$LOGON` and
consumes command answers off that stream. Neither *parses* in the sense of branching on
content — both `printf` what arrives — but `send_recev_client.c` matches answers
**positionally**, one `read()` per command, so it depends on the ordering of that stream and
an interleaved answer from another client desynchronises it.

**What that gives the decision:** removing the broadcast copy of an addressed answer would
make `recever_client.c` go **silent entirely** — it has no other source and issues nothing —
while `send_recev_client.c` would keep working, because §11.135 now delivers the addressed
copy it actually wanted. The two shipped clients are on opposite sides. Neither is a control
room, both are demonstrators, and that is itself part of the weighing.

**Observation, client-side, recorded not fixed and not minted as a row** (it is a
demonstrator in `util/`, not the application): `recever_client.c` reads up to
`SIZEBUFFER` = 128 bytes into a 128-byte buffer and `printf("%s")`s it; a full 128-byte read
leaves no terminator. Post-§5.73 the server sends answers up to 1024 B, so that client
overreads on any answer that fills its buffer.

## (i) An instrument hazard that cost this run ten minutes, discriminated both ways

**`timeout -s KILL` does not bound anything in this session type.**
`timeout -s KILL 3 sleep 30` returned rc=124 only after the child's **full 30 s**
`[measured]`; the `native1` run consequently ran 10 m 39 s past a 180 s bound and needed a
manual kill (its datum was already captured — §(a) is unaffected). Plain `timeout` is
measured WORKING on the same shape: `timeout 3 sleep 20` → rc=124 at **3 s**; an explicit
poll-and-`kill -9` watchdog → rc=137 at **3 s**. The mechanism is NOT attributed — SIGALRM
is neither blocked nor ignored in the inherited mask (`SigBlk 0`, `SigIgn` = SIGPIPE +
SIGXFSZ only), so the leading hypothesis (inherited signal disposition) is **refuted**.
`f30_alloc.sh` now uses plain `timeout` plus an orphaned-inferior sweep, with the
measurement in the comment. A successor bounding a launch with `-s KILL` will hang.
