## (b) The verdict at source: sizing-only, and decision-free

`[observed: src/tools/io.{cpp,hpp} at code d13681eb]` The arithmetic in the row is exact.
`setOutput` clamps to `MAX_BUFFER` = 1024 `[io.cpp:63, 364-368]`; `deliver` copied
`out.data + '\n'` with `strcpy` `[io.cpp:703]` and `broadcast` did it again `[io.cpp:725]`,
into `buffer = new char[bufferSize]` `[io.cpp:184]` with `bufferSize` = `tcp_buffer_in_size`
= 1024 `[observed: ~/.spacecrafter/config.ini:18; app.cpp:732]`. L + 2 bytes for an answer
of length L ⇒ L ≥ 1023 writes past the end.

The three things the task forbade changing, checked one at a time:

1. **Truncation behaviour.** Untouched: `setOutput`'s clamp is the only truncation on this
   path and it is not in the diff. **And the shared buffer never truncated anything** — a
   too-long message was not cut to `bufferSize`, it was written past the end. So the buffer's
   size expressed *no* policy that removing it could change. This is the sentence that makes
   the fix decision-free, and it is the one the row did not carry.
2. **Protocol output for currently-working answers.** The size rule is preserved to the
   letter: `send` still transmits `strlen(data) + 1`, terminator included (that is how a
   client frames a message — every harness reader splits on NUL). Only the storage changes.
   Measured: byte-identical on four binaries at six lengths (§(d)).
3. **Receive-path config semantics.** `tcp_buffer_in_size` still sizes exactly one thing —
   the buffer `SDLNet_TCP_Recv` fills `[io.cpp:487]` and `computeNewData` reads back, plus
   the HTTP file-streaming chunk `[io.cpp:611]`, which is bounded by it by construction.
   Nothing that is SENT is copied into it any more, which is what its name always claimed.

What the fix does change, stated because it is a claim the code carried: `SMALL_BUFFER_SIZE`'s
comment said the receive buffer *"must be larger than the messages that can be sent by the
server"*. That requirement is **retired at the site** with its record. It was never enforced
(no check existed) and the failure it was meant to prevent was the overflow itself.

## (c) The fix (I6 — the class, not the instance)

The defect is not "one `strcpy` is two bytes too long". It is that **`send()` did not carry
what it sends**: it read a shared member buffer whose size answers a different question, so
every sender had to `strcpy` into it first and every sender inherited its size. The root fix
is one signature:

    int ServerSocket::send(TCPsocket client, const char *data);   // io.cpp:743

All **nine** call sites pass their own message; the `send(TCPsocket)` overload that read
`buffer` is gone, and with it every `strcpy(buffer, …)` on the send path — `deliver`
`[io.cpp:712]`, `broadcast` `[io.cpp:736]`, `GOODBYE`, `SERVER_FULL`, `SERVER_OVERFLOW`,
`$NOTICE`, the `$LOGON`/`$LOGOFF`/`REQUEST ERROR` answers, and both HTTP 500 headers. The
HTTP 200 header is built where it is sent (a `std::string`, `header.size()` bytes, no
terminator — its rule, unchanged). `deliver` builds `out.data + '\n'` **once** instead of
twice and passes it to `broadcast` by `const &`.

Two of those sites were the same class waiting to fire, and are named rather than left:
`SERVER_OVERFLOW` was `strcpy`ed **over data just received** in the receive path
`[io.cpp:495 pre-fix]`, and every constant answer's fit depended on a configured size no
code checks. Not touched, with its reason: `fread(buffer, 1, bufferSize, file)`
`[io.cpp:611]` — a receive-sized scratch read, bounded by the buffer by construction, and
the one remaining legitimate use of `buffer` outside receiving.

## (d) Both ways, on the same drive — `harness/f28_send_buffer.py --mode overflow`

§11.121(m) `/proc/<pid>/comm` concurrent-instance assert and the frozen config/ssystem md5
in == out. ASan runs under `ASAN_OPTIONS=halt_on_error=0:detect_leaks=0`.

One drive, six answers, **shortest first**, so a binary that stops at the first fire has
still produced both negative controls. The lengths are computed **inside the launch** from
what it measures (one `get status planets_position` entry costs `name + 32 B`, measured
854 → 916 for a 30-char name), never from a constant carried between launches:

| step | command | payload | meaning |
|---|---|---|---|
| 0 | `search name m maxobject 320` | 854 B | fits — shipped |
| 1 | `get status planets_position` | 854 B | fits — shipped |
| 2 | + one 30-char body | 916 B | prices one entry |
| 3 | + one body, name computed | **1022 B** | **the LAST length that fits** |

discrimination.

## (g) Deviations and judgment calls

1. **Nine call sites converted, not two.** The mandate's shape was "size-to-message on the
   SEND copy". Converting only `deliver`/`broadcast` would have left `send(TCPsocket)`
   reading the shared buffer and seven senders depending on a configured size — the same
   class, disarmed only for today's longest producer (I6). Every converted site is a
   compile-time constant string whose bytes are unchanged, and `--mode logon` measures them
   on the wire pre/post.
2. **The ASan report count is a DISTINCT-PC count, not an event count.** ASan's default
   `suppress_equal_pcs` means step 5's overflow (2 bytes, same `strcpy`) is silent after
   step 4's. The pre/post claim is presence vs absence, which is what the DoD asks; no
   report was ever attributed to a count.
3. **`broadcast`'s own `strcpy` never appears in the pre-fix reports**, though it overflowed
   by the same arithmetic — with no `$LOGON` subscriber the compiler is free to sink a store
   whose only reader is inside the loop. Stated as an observation, not relied on: the fix
   removes the site regardless.
4. **`build-asan` needed `cmake .` before it would build** — its file list predated
   `SessionFile.cpp` (F20/F21) and the link failed on undefined `SessionFile::save/load`.
   Recorded so the next ASan user does not read it as a code defect.
5. **Date.** The dispatch's date is 2026-08-08 and the entry carries it; the last three
   launches ran 00:03–00:05 CEST on the 9th (artifact wall clocks are in the JSONs).
