## (a) The drain, mapped at source — and the row's three hypotheses answered

`[observed: src/tools/io.cpp at code d9de42ac]`

1. **It is drained, always.** `ServerSocket::run` calls `checkDataToSend()` on **every**
   pass of its loop `[observed: io.cpp:388]`, unconditionally — not only when a socket is
   active — and the loop's own wait is a 1 ms `SDLNet_CheckSockets` `[observed: io.cpp:375]`.
   `checkDataToSend` empties the WHOLE queue on each pass `[observed: io.cpp:630-639]`.
2. **It is drained to a socket SET that need not contain the issuer.** Each entry went to
   `broadcast()` `[observed: io.cpp:634]`, which sends to every client whose
   `clientBroadcastTab` entry is true `[observed: io.cpp:641-655]` — a table set true in

   `[observed: io.cpp:171]` and at close `[observed: io.cpp:685]`. With no subscriber
   `broadcast` returns 0, the entry is popped anyway, and the string is gone.
3. **The client COUNT is irrelevant** — hypothesis 3 refuted. One subscribed client

## (b) The root: the structure never carried the addressee

The origin of a request is known exactly once, at `computeNormalString(unsigned int client,
std::string string)`, and was dropped on the next line — `inputQueue.push(string)`
`[observed: io.cpp:625 pre-fix]`. From there on nothing downstream *could* address a reply:
`setOutput(std::string)` takes no addressee, and `broadcast` addresses a subscription. So
this is not a routing bug to patch at the send site; it is a structure that does not carry
what is asked of it (I6), and the fix is at the first hop.

**Delivered** (`io.hpp` `ClientMessage`, `io.cpp`):

- a request and an answer are a `ClientMessage {client, id, data}`; `inputQueue` and
  `outputQueue` carry it;
- a connection is named by its SLOT **and** by the id that slot held when the line was read
  (`clientIdTab`, `++lastClientId` on accept, cleared on close). Slots are reused, so the
  id is what makes an answer follow the CONNECTION rather than the number (I5);
- `getInput()` latches the request being served and **clears the latch when the queue runs
  empty** — the caller's batch is over, and output produced afterwards (a script, the TUI, a
  keypress) was asked for by nobody and must not be attributed to the last client that spoke;
- `setOutput()` stamps the answer with the latch; `deliver()` sends it to that connection if
  it is still that connection, and to the `$LOGON` subscribers, excluding the addressee so a
  client that is both gets ONE copy.

The interface is where the contract is stated (I1): `io.hpp` now says what `getInput`
latches, that `getInput`/`setOutput` are the application thread's and the server thread
touches neither, and what `setOutput` means by "outside the program".

## (c) The one thing this does NOT decide

Every byte that reached a client before still reaches it. The addressed copy is **additive**:
the `$LOGON` subscription is a channel of its own — a control room watching what every
operator asks — and it keeps receiving exactly what it received, minus the duplicate when the
subscriber is also the issuer. Whether it *should* keep receiving other clients' answers is a
semantics question about a channel whose own greeting says *"vous receverez maintenant les
logs"*; it is recorded as **§5.72**, not answered here. **VETO POINT** (implemented-and-live,
cheap to reverse: one condition in `ServerSocket::deliver` — broadcast only when there is no
addressee): the additive routing stands unless Vixy says otherwise.

## (g) Two things on this path had to be sound, and are fixed with it — the deviations

1. **`inputQueue` was pushed without the lock its pop side takes.** `computeNormalString` and
   the HTTP branch pushed from the SERVER thread `[observed: io.cpp:555, 625 pre-fix]` while
   `getInput` pops under `inputting` from the application thread `[observed: io.cpp:327-337]`
   — a `std::string` constructed into a queue another thread may be popping from. Taken
   because the routing this delivery installs READS what was pushed: the addressee decision is
   only as sound as the entry it is stamped from. Both pushes now go through `pushRequest`,
   which takes the lock. No new lock-order edge: the server thread takes `running` then
   `inputting`/`outputting`, the application thread takes those two alone, nothing takes them
   before `running`.
2. **`clientBroadcastTab` was never released** `[observed: the destructor, io.cpp:272-276
   pre-fix, releases `clientSocketTab` and `buffer` only]`. One-shot at shutdown, but this
   delivery adds a THIRD such array (`clientIdTab`), and fixing the instance while leaving its
   sibling is the I6 failure. Both are deleted now.

Both are inside the file the mandate points at, both are one line, and both are stated here
rather than folded silently.
