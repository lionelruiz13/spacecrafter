Regime split: **4 legacy-only · 33 composed-only · 105 both**.
      **The measurement that had to be got right first is READ vs WRITE**, and getting it wrong is what hides the finding in (b): `tex_halo` and `lighting` occur in `src/` ONLY as WRITES, in the two blocks that synthesize a star from a catalogue `Object` (`protosystem.cpp:102,105`, `ssystem_factory.cpp:390,393`). Counted as reads — which any `param["k"]` regex does by default — they look alive, and 180 dead lines of the field file stay invisible.
      **The census's own first version was wrong and the CORPUS caught it, not a review**: scanning `ModularSystem.cpp` alone reported 811 keys as legacy-only on the composed twins, which is not a believable number. The composed path does not read a section in one place — `loadBody` reads the node and then every module loader reads the same map — and `moduleLoader/` and `orbitModules/`, the directories base D names by name, had been left out. That is the criterion doing its job on the instrument.

    - **(c) → §5.125. ADOPTING THE COMPOSED FORMAT SILENTLY DROPS FOUR KEYS THE TWIN FAITHFULLY CARRIES.** `big_halo_size`, `tex_skin`, `halo_alpha_override` and `halo_scale_override` are read ONLY by `protosystem.cpp` (`:700,726,754`, `:667`, `:888-889`).     - **(d) → §5.126. ONE AUTHORED VALUE, TWO MEANINGS: THE TWO PATHS DISAGREE ABOUT WHAT "TRUE" IS, AND THE TWO SURFACES DISAGREE ABOUT CASE.** Both halves are measured at the code and both are reachable from shipped data.
      1. **Booleans.** The legacy loader reads `halo`/`hidden` through `Utility::strToBool` (`true`|`1` only); the composed loader reads the SAME keys through `Utility::isTrue` (`true`|`on`|`1`) at `ModularSystem.cpp:1243`/`:1400`. So **`halo = on` draws no halo on the old path and a halo on the new one** — one line making the comparison baseline and the new path disagree, which is exactly what §11.52(b) parity work assumes cannot happen from data alone. A third predicate, `Utility::isFalse` (`tools/utility.hpp:172`), runs the opposite way round for the module switches `hint`/`orbit`/`tail`: they are ON unless the value is `false`/`off`/`0`, so `hint = no` leaves the hint on.
      2. **Case.** `AppCommandInterface::parseCommand` lowercases every argument key (`app_command_interface.cpp:181`); **no stellar-system-file reader lowercases anything** (checked across every loader). So `orbit_Eccentricity` is a LIVE key on a `body action load` line — **3128 shipped script lines depend on it** — and a DEAD one in `ssystem.ini`. That asymmetry is the best available explanation for `[Sedna]`'s three CamelCase slips (`orbit_MeanLongitude`, `orbit_Period`, and `orbit_LongOfPericenter` with no `=` at all): the script convention, carried into a file that does not share it. The engine's own error messages spell those keys the same way (`orbit_creator_cor.cpp:184`, `:208`), which does not help.
      3. **Comments**, recorded here because it is the same shape: `ProtoSystem::load` treats `#` as a comment in COLUMN 0 only (`protosystem.cpp:134`) while `tools/ini_line.hpp` — the ONE line grammar since §11.115(b), used by every other reader of the family — treats one anywhere (`:16`). Three lines of the two legacy corpora carry a trailing `#` comment on a numeric value; all three are INERT today and measured so (`std::stod` parses the leading number and drops the tail), which makes this the §11.109(i) pair extended onto the comment axis rather than a live fault.
