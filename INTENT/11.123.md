# INTENT §11.123

123. **B12 — THE NEAR-SURFACE STAR FAMILY: DESIGN FIRST, THEN THE SLICE THAT RETIRES THE DARK SUN DISC (2026-07-31, Opus 5 executor dispatched by Claude Fable 5, task F9; code `3f137ef9` / `be6b2a84` / `a958c05e`, harness `8d1ea7e` / `36da647` / this entry).** Design note `claude/b12-design.md` committed BEFORE any implementation (the row's own shape, the F6 precedent); then the minimal slice: the Sun's disc EMITS and darkens toward its limb. §11.44's named residual — *"the new MESH lit-shades the self-lit Sun (dark disc in the surface regime)"* — **CLOSES**; the "one module cannot cleanly be both the far halo and the near surface" suspension is answered by a family, not by a flag.

- **(a) The design's load-bearing finding — EMISSIVE is not a regime, DETAIL is.** A star's photosphere has distance-invariant surface brightness (radiance is conserved along a ray), so the emissive base cannot be gated on proximity; and the recorded divergence is measured at **1 AU** (§11.44's zoom fov 30 from Earth), a *distance-far, screen-near* configuration. Any design that reads "near-surface" as a DISTANCE gate therefore fails the row's own acceptance measurement — recorded as rejected alternative A4 in the note, because it is the one a reader reaches for first. What the near regime adds is DETAIL, and its boundary is the G4 criterion applied honestly: *engage when the smallest structure the representation adds subtends ≥ 1 px*. For solar granulation (~1 Mm against R☉ = 696 Mm, a MODEL parameter of the procedural field, not a fetched datum) that is `screenSize ≥ 1/(g·viewportRadius)` = **0.68** at a 2048-wide render — inside the existing `screenSize > 0.2` band and close to the header's own wording for the surface slot. D4's two forcing reasons (VRAM, the 32k texture cap) do NOT apply to a star: the near representation is procedural, so it has no texture at all.
- **(b) The family, and how it replaces the MESH: by COMPETITION, not by suppression.** §11.44's sketch called for "MESH-suppression-for-stars"; the design needs no suppression rule anywhere. `deduceBodyModuleList` still emits MESH for any body with `tex_map` (unchanged), and the new `PhotosphereLoader` bids **200** where `BasicMeshLoader` bids 16 — so the star's ONE mesh slot holds the photosphere, every planet's holds what it held, and no draw path anywhere asks whether a body is a star (G6 answering the question it exists for; I4 kept). Members: `StarModule` (far, the big halo, untouched) · **`PhotosphereModule`** (near, the emitted surface) · a chromosphere module LATER, its own type (Q21's *"glowing around like an atmosphere … red … not uniform to match the prominences"* is a different geometry, a different blend mode, a different regime membership and its own state — four independent reasons for a distinct type). The bid reads **`isStar()`**, never the legacy `type` string: the composed format carries the same capability as `light_source = true` and `generateComposedTwin` emits it, so a twin re-selects the module. A `type`-string bid would have made every composed twin's star silently revert to the lit planet mesh — and that is exactly what the b24 RED leg below demonstrates.
- **(c) The law, DERIVED rather than recalled.** `bodyStarSurface.frag`: plane-parallel grey atmosphere, radiative equilibrium, LTE, Eddington closure ⇒ `S(τ) = (3F/4π)(τ + 2/3)`; `I(0,μ) = ∫S e^{−τ/μ} dτ/μ = (3F/4π)(μ + 2/3)`; normalised to disc centre **`L(μ) = (3μ + 2)/5`**. No measured coefficient enters, so the §11.51(d) red line is not approached — a band-specific `1 − u(1−μ)` coefficient would need a cited fetch and is recorded as a later refinement. μ comes from the drawn fragment (eye-space normal · direction to the eye), so it is exact at any distance and correct under body scaling. `L(1) = 1` ⇒ at disc centre the new path reproduces the OLD path's fragment (`body_sun.frag` = the texel, unmodified) exactly: the change is monotone and the centre is a parity anchor rather than a new value.
- **(d) MEASURED — the disc is no longer dark, and the law is on it.** Prediction fixed BEFORE the runs (design note §5.1/§10.3, committed in `8d1ea7e`); instrument `b12_photosphere.py` + `b12_limb.py`; ratio NEW/OLD per ring with the additive big halo removed (`body name Sun color halo r 0 g 0 b 0` — it feeds `StarModule` live), colour target `B8G8R8A8_UNORM` so the ratio IS the law, un-encoded. **Disc median (sum-of-RGB, max 765) 15 → 539, against the old path's 542.** Ring-median error vs the exact finite-distance law: **rms 0.0039 / max 0.0103** at 1 AU (fov 2, disc radius 268 px, big-texture branch), **rms 0.0049** at fov 20 (base level), **rms 0.0031 / max 0.008** at **d = 2.5 R☉** (the near approach, entered TWICE, both legs identical to 4 decimals). Per-PIXEL attribution over the disc interior — `|new − old·L(μ(pixel))|`, which leaves no room for a fitted global factor — **mean 4.08/255, bias −0.077** at 1 AU and **mean 4.34/255, bias −0.010** at 2.5 R☉; residual attributed to 8-bit quantisation (~3/540 per ratio quantum) plus the two paths' different mesh-LOD selection at the same pixel, both of which move the ring medians and neither of which has a preferred sign — consistent with the measured near-zero bias.
- **(e) The instrument can FAIL, demonstrated both ways.** The same analyzer run against the PRE-change binary refutes the same prediction: ratio **flat at 0.0277** across every ring (the ambient factor — `min(NdotL⁺ + Ambient, 1)` with `NdotL < 0` on a self-lit body), max error **0.9721**, per-pixel mean **142.6/255** with bias −142.6. RED and GREEN legs are the same script on two binaries.
- **(f) Star-gated inertness, settled by a 2×2 rather than by a single diff.** Two launches of each binary, same driver, three non-star scenes. Pairwise `px>32`: n1 Earth-surface `pre|pre2 = 0`, `pre|post2 = 0`, `pre2|post2 = 0`, but `post|post2 = 110` and every pair containing that one run = 110; n3 Mars identical shape (0 / 0 / 0 vs 4); n2 Moon (tessellated + big textures, the noisiest scene in every pairing) 0 / 19 / 19 vs 1097–1190. **Same-binary pairs span the full observed range, so the binary is not a discriminating variable** — one POST launch is an outlier against three agreeing runs, and the cross-binary pair `pre|post2` is 0 px>32 on n1 and n3. On the old path's own captures the change is **0 px at every threshold** (§11.52(b) holds by measurement, not by construction). `n4` (the Sun at native fisheye 180) is **0 px>0** — see §5.52 for why, which is a finding, not an absence of effect.
- **(g) THREE defects recorded, none fixed (stop boundary).** **§5.52** — in the depth-less mid band (`0.0015 < screenSize ≤ 0.008`) the new path draws **no body surface at all** while the old path draws it (measured with the halo suppressed: old row `178 720 725 … 270`, new row all zero); identical in both binaries, so it predates B12 and is a MESH/regime defect, not a star one. It also **corrects §11.44**, whose *"at native fisheye the disc is bright in both"* was reading the halo, not the disc. **§5.53** — the reduced and full levels of one colour map do not render alike (Sun disc centre `[253,246,218]` vs `[250,199,107]`, a 33 % luminance step), and the two paths cross the threshold at different sizes (old 180 px diameter, new 409) — a trap this task walked into (a near-approach ratio read 1.34 until the scene was moved above both thresholds) and the reason the reported near-approach figure is taken at d = 2.5 R☉. **§5.54** — two spellings of the G4 threshold family, the named px constants (`BODY_EARLY/FULL_VISIBILITY_BOUNDING_SIZE`) having zero consumers while `draw` gates on literals that are those values frozen at a 2048-wide render.
- **(h) ONE forced scope expansion, fixed at the class (`be6b2a84`).** The new set contract exposed a latent pool-sizing defect: pools are sized from the aggregate AT CREATION, so the FIRST contract to allocate a set fixes the first pool's per-type budget — and the first body loaded is the Sun. A one-texture star-surface contract therefore sent every later six-texture layered set into a four-texture pool: `WARNING-VkDescriptorSetAllocateInfo-descriptorCount`, *"will fail on others"*, **7 per run, 0 before**. This is `poolTypeMask`'s own defect class one dimension over (that comment already says a pool made before a contract introduced a TYPE cannot serve it; nothing said the same about COUNTS), so the fix is at the class: `allocSet` compares the contract's PER-SET need against what the current pool was sized to serve and takes a new pool when one set would not fit. Measured **7 → 0** validation warnings on the same battery; forced because the zero-validation bar is the task's own gate and the message names a portability failure, not a nuisance.
- **(i) I2 obligation discharged (`3f137ef9`).** The colour-map state machine (authored map / runtime SKIN / big-texture level) is now ONE authority, `SkinnableColorMap`, used by both mesh types; each type keeps its own family, set and binding. The skin seam is not decoration on a star: the shipped Sun's own data carries `#tex_skin = bodies/sun304A-sdo.jpg`, so dropping it would have silently retired a demonstrated operator use. **Exercised on the star, `b12_rare.py`, 15/15 green**: `skin_use` before any skin is a no-op; creating a skin does NOT activate it; `skin_use on` changes the disc (`[177.6, 37.5, 6.3]` vs base `[226.4, 177.5, 86.1]`) and `off` reverts, **twice**, the second entry starting from the first exit's state and landing on the same values; replacing a skin while active deactivates it (old parity); hide/show the star twice (disc `[0,0,0]` hidden, exact restore); the big-texture threshold crossed both ways twice with exact restore. The generality that WAS dropped is named and proved inert: the photosphere does not declare `BMT_PROJECT_G1_SHADOW`/`BMT_RECEIVE_SHADOW`, and the shadow orchestration already skips `isStar()` bodies in the caster scan, the receiver scan and the self-shadow nomination (`ModularSystem.cpp:321, 375, 404`) — those bits have been declared on the Sun's mesh since row 1 and never once selected. `drawTrace` and the big-texture path are kept.
- **(j) D11.** Instrument = `b39_cost.py`'s (the reference body's `evalCount` delta over an undisturbed 20 s dwell, frozen sim time). FAR (fisheye 180), NEAR (fov 2, disc 537 px, big texture), NOSUN (the same framing with the star hidden = the family gated off) and NEAR2 (the reversible pair's second entry): **3225–3226 frames per 20 s in every scene and both binaries**, i.e. the frame cadence is pinned and the family is not distinguishable from its absence. Honest limitation, stated: the cadence is capped (161.3 fps), so this bounds the family only at the instrument's quantum of **1 frame in 3226 ≈ 0.6 µs/frame = 0.06 % of the 1 ms budget**; it does not resolve GPU headroom. The structural half of the claim carries the rest [derived]: the module's per-frame CPU work is a strict subset of `BasicMesh`'s (same binds, same draw, minus `fillPlainShadows`), and its fragment adds one `normalize` + one `dot` + one `fma` while REMOVING the shadow-sampling branch — with zero cost in the halo-only regime, where no surface module is invoked at all.
- **(k) D9/D13: the slice costs NO product surface.** No new data key (the module reads `tex_map`, the STAR bit and the body's colour, all existing); no new `module =` value (it fills the existing MESH slot and `getType()` returns MESH, so the twin emits `module = MESH` exactly as before); nothing is written anywhere, so D13 is neutral. - **(n) What the CONTENT slice must know.** The lineage is the old `StarViewer`, which is the design's reference implementation and is still unreachable: `big_star.frag` already carries 4-octave value noise (granulation) and a two-simplex product (spots) driven by the global `time`, and `big_star_corona.frag` is the chromosphere's ancestor (a screen quad at 4× the disc, additive, noise-offset).
