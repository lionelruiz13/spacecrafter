## (a) The renderer did not have to be extracted, and that is the finding

The task said *share, never duplicate* — and the composition was already a pure
static on the writer's own class: `ScriptAnnotator::withAnnotation(line,
message)`, public since §11.184, with `withoutAnnotation` and `annotationBegin`
under it `[observed: script_annotator.hpp:73-78, .cpp:43-66 at 1014e5a5]`.
Sharing therefore cost **no new composition code at all**: the log CALLS the
writer's function — including its idempotency rule, so a `#!` tail already on
the line is REPLACED in the rendering and never doubled. What the log line shows
is byte for byte what the writer would land on that line, by construction rather
than by agreement.

This is worth naming because it sharpens §11.193's Root 1. The RECORDS coupled
rendering to writing; the CODE had already separated them — a static that takes
a line and a message and knows nothing about files. The shape the owner
predicted was one call away the whole time, and no reader of the records could
see that. A record that says less than its own code is a specific failure mode,
and this is an instance: §11.184's contract describes `withAnnotation` as part
of the writer's machinery rather than as the rendering the writer happens to be
the first consumer of.

`AppCommandInterface::errorLine(message)` is the origin-prefixed rendering, and
the only new function `[observed: app_command_interface.cpp:258-274 at
9a3b7a55]`:

```cpp
const std::string where = currentOrigin.where();
const std::string raw = currentOrigin.lineText();
if (where.empty() || raw.empty())
	return std::string();
return "Error executing " + where + ": " + ScriptAnnotator::withAnnotation(raw, message);
```

Two consumers, both already written to by §11.187(d): the funnel
`executeCommandStatus` and the sibling that bypasses it. Neither composes
anything of its own.

Two legs make this more than a table. **The recomposition leg**: the expected
line is composed by the INSTRUMENT, from the script file's own bytes and the
message, through `harness/f73_line.py` — a re-implementation of §11.184's tail
rule (first `#!` at or after the first `#` outside a `"…"` run), never the
engine's function. Two independent renderings agreeing is evidence; asking the
engine what it should have printed is not. **The joining leg**: the post line
equals `rendered(origin, X, Y)` where `X` is what the PRE binary's first line
said after `Could not execute: ` and `Y` is what the PRE binary's second line
said — so the collapse invented nothing and dropped nothing, asserted as string
equality against the other binary's own output in the same run.

## (c) The collapse stops exactly where the origin does, and that is one predicate

`errorLine` asks TWO questions — `where()` for a NAME, `lineText()` for a LINE —
and returns empty unless both answer. Every origin this engine produces answers
both or neither: FILE and TCP carry the line they were read from
`[observed: script.cpp:119, app.cpp:780]`, and NONE (nested, UI, mkfifo, HTTP)
carries neither `[observed: script_origin.hpp:78-101; lineText/where at :103-125]`. So the legacy two-line
form is reached by exactly the origins §11.184's nesting rule protects, and it
is byte-identical there — including the tag, which stays in that branch so the
branch is behaviour-preserving for any origin combination that could ever reach
it.

Asking both is not belt-and-braces. A future producer with a name but no line
would otherwise log a tail with nothing in front of it; one with a line but no
name would log `Error executing : `. This is §11.192(b)'s form of argument
applied to a second predicate, and the fallback is a shape that already exists
rather than a new one.

**Measured, not assumed**: the nested refusal keeps both its lines on BOTH
binaries, and the leg that says so is one of the two f69 legs that needed no
edit at all `[measured: f68 leg iii, f69 leg viii]`.

## (d) The block-structure diagnostic: the addendum's leg, and the barrier §11.184 owed

The owner's re-execution argument bites hardest where the tail actually LANDS —
the ruled class, whose diagnostic is `reportScriptError`, not the funnel. That
line quotes the offending line in brackets, so on the SECOND execution of an
annotated script it quoted the tail the FIRST execution had written:

```
run 1  script <f>:2: this 'struct loop end' closes nothing: … [struct loop end]
run 2  script <f>:2: this 'struct loop end' closes nothing: … [struct loop end #! this 'struct loop end' closes nothing: …]
```

`[measured: f68 leg x, PRE binary, artifacts/f73/f68/f68_result.json]` — the
same error, logged differently the second time, on the common path.

The fix is one expression: the bracket quotes
`ScriptAnnotator::withoutAnnotation(quoted)` — the writer's own tail rule, so
the two cannot disagree about what a tail is. The WIRE's subject keeps the raw
text byte for byte (`quoted` itself is unchanged), which is why this touches the
log and nothing else.

§11.193's own correction names what this is: §11.184/F63 measured the write's
delta on the FILE channel and the EXECUTION channel and never enumerated the LOG
as a channel of that same delta — I7's failure mode, *"verify the channels you
think of, leak on the one you forget"*. **This is the barrier I7 requires,
shipped one entry late.** The leg is both-ways by construction: post logs the
same bytes on both executions, PRE logs a longer line the second time, and both
binaries leave the file byte-identical after the second execution (the writer's
idempotency, re-held through the shared function).

## (e) Judgment calls, each with its argument and its veto

1. **`Error executing <origin>: ` for BOTH origins** — the owner's example
   spelling for the file case, extended to TCP. Argument: the collapse deletes
   the words *"Could not execute"*, which were the only thing on those two lines
   saying an error had occurred; without a replacement, `tcp#3: get status
   nonsense #! …` reads like an echo of a command rather than a refusal of one.
   A TCP line loses exactly the same words as a file line, so a prefix rule that
   differed between them would leave one channel worse off for no stated reason.
   **Veto-open**: the dispatch sketched `tcp#3:` bare for TCP; if the owner
   prefers the asymmetry, it is one branch in `errorLine` and the gates read
   the prefix from `f73_line.PREFIX`.
2. **TCP unified with FILE** — §11.193(c)3 marks this [derived]; the owner's
   statement is about file scripts. Kept unified because non-duplication is a
   property of the error's rendering, not of its channel, and because the TCP
   line IS the raw line (`fromTcp(id, out)` stores exactly what was executed),
   so the intent-modified line is well-defined for it. **Veto-open, flagged
   here as the spec asked.**
3. **`reportScriptError` keeps its own FORM** — it now uses the anchor's tail
   rule (d) but still renders `script <origin>: <what> [<line>]` rather than the
   intent-modified line. Three reasons: the task scoped the collapse to the
   funnel and its sibling; §11.192's table measured that line as unmoved and
   this task's bars include F72's; and its shape is owner-accepted at §11.184.
   **But it is a second FORM for the same information class**, which §11.193(f)'s
   anchor-first view says a sink should not have — *"the form belongs to the
   anchor and comes down"*. **Veto-open and named**: unifying it would replace
   that line with `Error executing <origin>: <line> #! <what>`, one call, and
   would retire the `[quoted]` form §11.184 shipped. Not mine to decide.
4. **`ScriptOrigin::lineText()`** — one definition of "the line with its ending
   stripped", used by the renderer and by `reportScriptError`'s subject (which
   had the loop inline). The wire's subject is computed by it now; the f69 legs
   assert the resulting bytes are identical to F68's and F70's recordings, so
   the refactor is certified on the channel it could have moved.
